Property panels, node editors, and Figma-likes — what's actually reusable, and where the schema comes from

Report 1 answered "which headless kit for behavior, which system for the visual layer." This one asks the question underneath it: is there a real sub-assembly anywhere for the property rail, the sliders, the inspector chrome around a canvas — and once Zach reweighted the question mid-research, where does the schema those panels render actually come from. Two research passes, twelve real codebases, read from primary source.

Where report 1 left off: ui-design-system-strategy-2026-09-07.html split the chrome problem into two axes and answered them separately — Axis 1 (headless behavior primitives: focus traps, dismissal, ARIA) converge on Base UI, one file at a time, never big-bang; Axis 2 (the visual system: semantic color roles, scheme invariance) keep the shipped --ss-* token layer, because the dark/light bugs were palette-derivation math inside it, not a missing library1. Correction in flight on that report: its central Axis-1 argument — that Base UI's outside-press dismissal is an unconditional capture-phase listener, "structurally immune" to the stopPropagation-starvation bug class in docs/bugs/0002 — did not survive independent adversarial verification; Base UI's actual outside-press handling turned out to be conditional, not unconditional2. This report doesn't re-argue that point; it just doesn't repeat it. What follows is orthogonal to both axes: not which headless kit to standardize on, but whether a reusable property-panel — the sliders, typed fields and inspector chrome sitting on top of whichever kit — exists anywhere to build from, and, once Zach reweighted the question mid-research, where the schema those panels render even comes from.
Verdict, in one breath: no importable property-panel exists anywhere in either survey — every actively maintained node editor and every actively maintained design tool hand-assembles its own, on top of a headless-primitives library used narrowly for popovers/menus/dialogs. But the pattern converges hard: a typed field-spec union plus one small dispatcher, which is exactly the shape SystemSketch's own 51-entry FieldSpec already has35. The deeper, more valuable finding is Zach's own reweighting: the interesting variance across twelve real codebases isn't in the widget-dispatch layer, it's in where the schema itself comes from — hand-maintained (the majority), introspected at runtime from the real object (Langflow), or compiled at build time directly off the parameter's own type declaration (Graphite) — and that last one is a genuinely different mechanism worth a real look, not a recommendation to switch to today.

The meta-question — is there a shared property-panel subassembly? No cross-project library exists; nobody npm installs a common "node-property-panel" package. But there is real convergence, in two layers. The headless-primitive layer is a shared kit, just a generic one: four of six modern apps sit on the Radix family (Langflow, Sim Studio, Activepieces on @radix-ui/react-*/radix-ui; ComfyUI and n8n's v2 layer on reka-ui, Radix's Vue port); Dify is the outlier on Base UI3,7,11,14,16,18. That layer knows nothing about "node properties" — it's just Select/Popover/Dialog/Slider. The domain-dispatcher layer is where the real pattern lives, and every app except Dify hand-builds the identical shape: a typed field-spec/parameter-type union, declared by whoever authors the node, fed through one small frontend dispatcher — a map literal (ComfyUI), a switch inside one function (Langflow, Activepieces), a switch inside one component's render method (Sim Studio, most exhaustive at ~40 cases), or the same idea degraded into an unfactored conditional chain (n8n)4,9,13,17,19. Honest answer: the architecture is copied everywhere but Dify; the code implementing it is reinvented in every single repo. The transferable thing for SystemSketch is the shape — one declarative field-type union, one dispatcher, built on a headless-primitives library — never a dependency to add.

Pass 2 — Figma-like design tools

The deep section. Penpot gets real space — it's the richest independent finding of either pass. Graphite gets real space too — its Rust macro-attribute mechanism is the standout for §4 below.

Penpot the richest single find

penpot/penpot · MPL-2.0 · tip 5b97fb9, package.json v2.17.0 · 680 .cljs/.cljc files + 294 .scss files under frontend/src — a mature, large system, checked from primary source, not a landing page21

Still ClojureScript; the WASM renderer is real but opt-in

Confirmed via frontend/deps.edn and shadow-cljs.edn: UI components use rumext (a separate open-source React wrapper, same "funcool" authors as Penpot's other core libraries), supplying the mf/defc component macro, hooks, and a Malli-based prop-schema mechanism22. Canvas rendering is two engines side by side, not a finished migration: render-wasm/ is a genuine Rust crate on rust-skia, but features.cljs:28-65 shows the rollout priority — URL param > user profile > team flag — defaulting to :svg, the legacy ClojureScript/SVG-DOM renderer23.

The options/inspector panel

frontend/src/app/main/ui/workspace/sidebar/options/: ~24 reusable widget-group files (fill, stroke, shadow, layout_container — 61KB, Auto Layout — typography — 39KB — component — 57KB), one file per shape type composing them24. No general component library anywhere in the ClojureScript tree — every widget is hand-built in ui/ds/. One real exception: a brand-new, separate React+TypeScript package (@penpot/ui) on react-aria-components — but it exports exactly one component (Modal) as of this checkout, not yet used to replace the ClojureScript controls25.

Numeric drag-scrub, color picker, combobox — all fully custom, no library

ds/controls/numeric_input.cljs (863 lines): a Pointer-Events state machine (:idle → :maybe-dragging → :dragging), native setPointerCapture/releasePointerCapture, a 3px movement threshold separating click-to-focus from drag-to-scrub, modifier-scaled step (drag Shift=×10/Ctrl=×0.1; keyboard Shift=×10/Alt=×0.1 — a real inconsistency between the two modes worth noting before copying it), and the whole scrub gesture wrapped in one undo transaction26. The color picker (~2,000 lines) and the select/combobox listboxes (manual getBoundingClientRect positioning — no floating-ui/popper anywhere in the repo) are equally hand-rolled27,28.

The internal design system admits it's incomplete

ds/_sizes.scss:8 carries the literal comment // TODO: create actual tokens once we have them from design — even Penpot's own chrome DS is hand-authored Sass, not fed by Penpot's own token-generation product feature. The tip commit checked was literally "Migrate editable-select to DS icon* and design tokens (#11500)" — an active, ongoing migration29. Drag-to-reorder in the layers panel is hand-rolled too, despite react-virtualized being a real dependency — it's used exactly once, for a font list, not the layer tree30.

Dispatch: a hand-assembled case, not a declarative field-spec

single-shape-options* is a case shape-type over :frame/:group/:text/:rect/:circle/:path/:svg-raw/:bool; multi-selection is a separate branch, not a generic N-shapes-to-generic-diff-UI layer31.

The mixed-value fold — a direct, independent validation of SystemSketch's own mechanism

This is the most reusable idea in the whole survey, and it lines up with code SystemSketch already shipped. multiple.cljs defines a type→read-mode table (shape-type × attribute-group → how to source that attribute) and folds every selected shape's values through app.common.attrs/get-attrs-multi — fully framework-agnostic, plain Clojure, no React/DOM: walk every shape per attribute; agreement keeps the value, disagreement collapses to the sentinel keyword :multiple; a missing attribute is skipped, not treated as a mismatch. Numeric comparison uses epsilon-tolerant equality specifically to stop floating-point jitter from falsely flagging "different." Domain-specific equality functions are plugged in per attribute group where naive equality is wrong (shadow and blur lists strip their own :ids before comparing, so structurally-different-but-visually-identical still counts as "same")32. The sentinel flows down as a real typed value, not a UI flag — numeric_input.cljs's own prop schema types its value as [:maybe [:or :int :float :string [:= :multiple]]], and each leaf widget independently decides how to render "Mixed"33.

Independent validation, confirmed by reading the file at build time (not pasted from the leg): SystemSketch's own property-rows-mature worktree arrived at the identical shape from a completely different substrate. src/uiEditor/tabs/systemPrimitivesModel.ts:398 currently reads export interface PropertyRowDef<State> { — PropertyRowDef.get returns tldraw's own SharedStyle<RowValue>, a {{type:'shared'|'mixed'}} discriminated union rather than a bare string sentinel. Its own WHY comment (confirmed present, confirmed) names Penpot's string-sentinel approach as the rejected alternative — reasoning that a magic 'mixed' string type-checks fine wherever a real value was expected, so a widget that forgets to check it reads the sentinel as data instead of failing to compile; the wrapper type makes every read site exhaustive-checkable instead34. Two mature tools, two different languages, arriving at "compute mixedness once as a pure fold, let each widget render the sentinel" independently — and one of them already named the other's approach and chose not to repeat it.

Design tokens — the product feature and the app's own chrome are separate pipelines

The user-facing DTCG feature is real and substantial (real style-dictionary and @tokens-studio/sd-transforms deps, plus a computed-token expression language). Penpot's own chrome theming is separate hand-authored CSS custom properties compiled from Sass — the two pipelines don't share code; Penpot's UI does not dogfood its own tokens product34.

Honest reusability assessment

Nothing is directly importable — ClojureScript/shadow-cljs, no published npm package of the DS widgets; @penpot/ui's bet on react-aria-components is a real technology signal, but the package itself (one component) is too immature to depend on. What's worth copying directly: the shape-type case dispatcher, the mixed-value fold as a pure domain function, the numeric-input drag-scrub state machine, and the type→read-mode sourcing table. Not worth copying: the hand-rolled listbox positioning code — Penpot's own newer package already abandoned that in favor of react-aria.

Graphite's macro-attribute mechanism — the standout finding

Graphite's properties panel (Properties.svelte) renders a generic WidgetLayout.svelte fed by a propertiesPanelLayout store — zero per-node-type UI code on the Svelte side44. That layout is built in Rust: node_properties.rs (2,985 lines) is a library of generic, type-keyed widget builders (number_widget, color_widget, vec2_widget, font_widget, blend_mode_widget, bool_widget…)45. The widget choice is declared as a macro attribute directly on the node's own parameter, in the node's own definition file — extract_xy.rs:26 → #[widget(Radio)]; adjustments.rs:42 → #[widget(Dropdown)]; a text node → #[widget(ParsedWidgetOverride::Custom = "text_area")]; a blend node → #[widget(ParsedWidgetOverride::Hidden)]46. A proc macro (node-macro/src/lib.rs:23, codegen.rs:158-232) turns that attribute into compile-time per-parameter metadata; at runtime an overrides map layers in min/max/step/unit/mode, with a small (~20-node) hand-written escape hatch for composite panels a single-widget-per-parameter model can't express (curve editors, multi-field color grading)47. This is a genuinely different mechanism than "generate a form from a JSON schema" — the schema lives as an attribute on the parameter, next to the node's real logic, so the widget hint can never drift out of sync with the node's real signature. See §4 for what this means for SystemSketch.

Cross-cutting pattern across the comparables

Across every actively maintained example — Excalidraw, tldraw, Open Pencil, AFFiNE, Webstudio — the property/style panel is hand-assembled per property/action, on a headless primitives library used narrowly for popovers/menus/dialogs, never schema-generated. Graphite is the one clear counter-example, and it earns that architecture because its property data comes from a compiled Rust type system with a real proc-macro attaching UI hints at the parameter's declaration site — SystemSketch has no equivalent today (Python dataclasses could theoretically play that role; no macro/decorator does yet). The realistic near-term precedent for SystemSketch is the Excalidraw/tldraw/Open Pencil shape it's already converging on, not Graphite's, unless a dataclass-driven widget-hint mechanism becomes a deliberate goal.

The deeper layer — where does the schema come from

Zach's reweighting, mid-research: "we can also measure the back end implementation of how they manage all the different values and properties — that may even be a bigger learning point." He's right that this is the deeper question. Every project above answers "which component renders a slider" — that's the shallow half, and §2/§3 show it converges on the same shape everywhere but Dify. The harder, more valuable question is where the property schema itself originates, and whether it can drift from the real underlying object it describes. The survey turned up three real positions, plus one worth its own mention as a middle case.

1 · Hand-maintained, separate from the object — the majority case

A human writes the schema once, by hand, in a file distinct from the object it describes. This is what almost everyone in this survey does: SystemSketch's own 51-entry FieldSpec35; Foxglove/Lichtblick's SettingsTreeEditor (cited in report 1)1; Sim Studio's SubBlockConfig[]17; n8n's INodeProperties13; Activepieces' PropertyType, itself from a shared piece-authoring SDK19. It works, and it's what's shipped everywhere — but the schema and the object it describes are two files that can silently drift apart.

2 · Derived from the real type, at its declaration site — Graphite alone

Graphite's #[widget(Dropdown)] Rust macro attribute lives directly ON the node parameter's own type declaration, compiled at build time into per-parameter metadata46,47. The widget hint literally cannot drift from the parameter's real type — the compiler would reject a mismatch. Genuinely different from a JSON-schema-driven form; no other project in either survey does this.

3 · Pure domain-level computation, decoupled from rendering — Penpot

A related but distinct question: not "where does the field's type come from" but "where does a computed fact about a selection (is this mixed?) come from." Penpot's get-attrs-multi is a framework-agnostic fold with pluggable per-attribute equality, completely separate from how any widget renders the resulting sentinel32 — the same separation of concerns SystemSketch's own SharedStyle-typed get already has34. Worth naming alongside the other two because it's the same underlying instinct — keep the truth outside the widget — applied to a different layer of the problem.

1.5 · Runtime-introspected from the real object — Langflow, the middle case

Langflow's schema is emitted at runtime by the backend introspecting the actual Python component's declared Input class attributes (StrInput, IntInput, DropdownInput, … — each carrying field_type/value/input_types/options, not a bare type hint)9,10. Not pure type-hint inference, and not a fully separate hand-maintained frontend spec either — an explicit, parallel declaration layer the component author writes alongside the class, richer than a signature but carrying its own upkeep cost.

Directly relevant to Pyblocks: Zach raised this three-way framing and will read for it. Pyblocks today infers a block's ports purely from its Python function signature — position 2's cousin, but without a macro, so there's no compile-time metadata layer, just runtime reflection over the signature. The three positions above are the three directions that could take: stay with pure function-signature inference (current Pyblocks, cheapest, most constrained — a signature alone can't carry a widget hint, min/max, or a dropdown's options); add an explicit parallel Input-declaration layer (Langflow's way — richer, human-authored, can drift from the signature it sits beside); or annotate the type at its declaration site (Graphite's way — Python's own dataclass/typing machinery could plausibly carry this, via a decorator or metadata field on a dataclass field, though nothing in Pyblocks does this today).

Verdict for SystemSketch, stated as an open question, not a recommendation: its own FieldSpec architecture is already validated as the right shape by two independent convergences — Foxglove's SettingsTreeEditor1, and now this survey's majority (Sim Studio, n8n, Activepieces, and by extension ComfyUI/Langflow's frontend dispatchers). The genuinely open question this survey raises, which it does not answer either way: is it worth moving from hand-maintained toward type-site-derived (Graphite's model), given Python's own dataclass/typing machinery could plausibly play that role for SystemSketch's own Block parameters? This is a real, undecided architectural question to put in front of Zach — not a call this report makes for him.

Cross-cutting synthesis, against the two original hypotheses

The original brief carried two competing hypotheses. The evidence across both passes answers them cleanly, not by splitting the difference:

(a) Rich property panels are inherently custom-built everywhere, regardless of headless-kit choice

Confirmed strongly. Every actively maintained app in both surveys — twelve real codebases across two ecosystems (node/flow editors and Figma-likes) — hand-assembles its own panel. Radix, Base UI, and Reka UI only ever supply the popover/dialog/slider primitives underneath; not one of them supplies the panel itself. Even Graphite, the one project with a compiled schema, still hand-writes ~20 whole-node overrides for panels a generic model can't express47.

(b) A real reusable panel architecture exists, worth studying structurally

Also true — but the valuable transferable thing is never an importable package; it's the architecture pattern: a typed field-spec union plus one small dispatcher (ten of twelve projects), or Graphite's type-site macro annotation (one project, a structurally different and arguably stronger answer to the same problem).

Which hypothesis the evidence actually supports, stated plainly: (a) is the operative finding — there is no sub-assembly to adopt, full stop. (b) is real but is a statement about architecture, not about a dependency; treating it as "go find the library" would send the wrong signal. SystemSketch is not behind for lacking one; it already independently built the same shape the majority of this survey converged on.

Updated / reaffirmed recommendation

No change to report 1's Axis 2 answer: keep the --ss-* token layer. Nothing in either pass here bears on scheme invariance or palette derivation — property panels and design tokens are orthogonal concerns, confirmed again by every project surveyed keeping them in separate systems (Penpot's own DTCG feature vs. its hand-authored chrome Sass is the clearest example)34.

Report 1's Axis 1 framing is being corrected separately (the Base UI "structurally immune" claim, per the recap above) — this report doesn't reopen that question. What this report adds is a layer report 1 didn't cover at all: the property-panel architecture sitting on top of whichever headless kit is chosen.

SystemSketch's own FieldSpec approach is validated as sound — a typed field-spec union plus one small dispatcher is the pattern ten of twelve surveyed projects converge on, independently, from Foxglove's C++/TS substrate to Sim Studio's TypeScript to Penpot's ClojureScript. Nothing here argues for replacing it. There is one live open architectural question, deliberately left undecided: whether SystemSketch's schema should eventually move from hand-maintained toward type-site-derived (Graphite's model), using Python's own dataclass/typing machinery — flagged for Zach in §4, not resolved here.
