Members of a Block, authored like ports

Proposal, then built the same day · 2026-09-09 · measured against cd25d846 · tldraw 5.3.2 pinned · jump to what shipped

Recommendation. A member is what an Expanded Block's direct child Block already is — tldraw's parentId, already replicated across every linked occurrence by the definition body sync. So do not add a second membership model. Add the three things that are missing: a Members section in the inspector that mirrors Inputs/Outputs (list, grip reorder, +), an authored order that is tldraw's own child index, and a live stack layout on the parent driven by three numbers — gap, gutter, width: fill | own — with Inset and Edge-to-edge demoted to presets that write those numbers. One rule keeps a definition from being sized by two parents: Fill only ever writes an occurrence's Port/Simple box, and an Expanded child is always Own and drives its parent. Blocks do not store their parents; parentId plus linkedBlockOccurrences derive them, and PEP 0004 already ruled that a stored stamp loses to containment.

Where this changes the brief. "Add children like ports" reads as if children need building. They exist, they sync, they export, and Inset/Edge-to-edge already paints them. What does not exist is order as an authored fact, layout as a live constraint, and the list. That reframing is why the plan below is ~5 files, not a new primitive.

3 · The model

3.1 Membership is parentId; order is the child index

A member of Block P is a Block whose parentId is P. tldraw already keeps an authored, fractional index on every child and exposes it through getSortedChildIdsForParent. A vertical stack has no meaningful z-order of its own (nothing overlaps), so the index is free to mean stack order. Reorder in the list = rewrite indexes with stock getIndicesBetween; the layout pass then places them. No new array, nothing to keep in sync, and duplicate/paste/undo keep it right because tldraw maintains it.

3.2 Four optional props on the parent, no migration

// src/blocks/blockModel.ts — all optional: every saved Block reads as today
bodyLayout:   T.literalEnum('free', 'stack').optional(),   // absent = 'free'
memberGap:    T.number.optional(),                          // absent = preset default
memberGutter: T.number.optional(),                          // absent = preset default
memberWidth:  T.literalEnum('fill', 'own').optional(),      // absent = 'fill' (today's behaviour)

// memberLayout: 'inset' | 'edge-to-edge' stays — it is still the PAINT style
// (cards with radius vs one joined stack) and the preset that seeds the numbers.

export function blockMemberSpacing(props): { gap: number; gutter: number } {
  const preset = blockMemberLayout(props) === 'edge-to-edge' ? 0 : BLOCK_MEMBER_GAP_PX  // 12
  return { gap: props.memberGap ?? preset, gutter: props.memberGutter ?? preset }
}

Pressing Inset or Edge-to-edge sets memberLayout and clears both numbers. Typing a number leaves memberLayout (the paint) alone and sets the override. The preset button lights only when the effective numbers equal its pair, so the UI never lies about hidden state.

3.3 Free vs Stack

bodyLayout: 'free' is today: a frame, children wherever they were dropped, Inset/Edge-to-edge as the one-shot command it is now, with its WHY intact. 'stack' is the new mode: the parent lays its member Blocks out continuously, and a Block dropped into it takes the slot under the pointer instead of a free position. That is Zach's "when you add children you cannot add blocks to the parent in the free sense" — as a mode the author enters, not a rule that fires on existing boards. The first Add member from the inspector flips a free Block to stack (D7). Non-Block children (a sticky, a callout) are not laid out and keep floating (D5). Cables are children too and are already excluded from clipping; the pass ignores them.

3.4 The live pass

// src/blocks/memberStack.ts — mirrors installBlockAutoResize exactly
installBlockMemberStack(editor):
  side effects (create / change / delete of any shape) → note every stack ancestor
  settle once after the operation; never while isBlockAutoResizeGestureActive()
  for each dirty stack parent, history-ignored, guarded against its own writes:
    frame   = layoutBlock(parent.props)           // header.h, footer.h — the app's own geometry
    members = getSortedChildIdsForParent(parent)  // authored order
              .filter(isBlockShape)
    {gap, gutter} = blockMemberSpacing(parent.props)
    y = frame.header.h + gap
    for m in members:
      w = memberWidth === 'fill' && m.props.view !== 'expanded'
            ? parent.w - 2*gutter : m.props.w        // Rule 4: Expanded children are Own
      write m.x = gutter, m.y = y, m.w = w (via resizeBlockProps, keeps views[] honest)
      y += m.h + gap
    if parent.autoResize:
      parent.w = max(own widths of Own members) + 2*gutter  (only if some member is Own)
      parent.h = y + frame.footer.h

Why this is not a feedback loop: the only parent field read by children is w, and the only child field read by the parent is the w of members it did not just write (Own). Fill children never feed the hug, so the fixed point is reached in one pass. When every member is Fill and auto-fit is on, width is authored and only the height hugs.

3.5 Rule 4 — one definition, many parents

Zach's worry is precise: a Block that is a member of two parents "can only have the one width in the expanded view". The tree confirms it is one field. Occurrences of a definition share views.expanded (and body, ports, description, type); the Port and Simple boxes are per occurrence. So:

Fill writes only the occurrence's Port/Simple box. An Expanded child is always Own and drives its parent. A parent may size the instance it holds; it may never reach through the instance into the class. The stack pass enforces it (one branch), and a unit test proves views.expanded is byte-identical before and after any stack pass. This is exactly the working rule in Zach's note — "in expanded view we generally don't drive the width; in port view we drive the width and do edge to edge".

"Each block needs to know its parents" therefore needs no field. One occurrence has one parentId; a definition's parents are linkedBlockOccurrences(editor, block).map(o ⇒ parentBlock(o)), derived on demand for the inspector's "Used in: A, B" line. PEP 0004 already decided that a stored owner id is a fallback that loses to containment; storing a parent list here would reopen that bug class on paste.

4 · The inspector — Members section

Cloned from Inputs/Outputs: uppercase label, count pill, +; rows with a grip (dnd-kit handle, ↑↓ to step, no SortableContext, same as ports), the member's icon, its title in mono, its type, a view badge (S/P/E) for the occurrence, and ⋯ for Remove from stack (stock reparent to the page, page position kept — the existing "Remove from container" path), Unlink, Delete. Clicking a row selects the member on the canvas, so the inspector then shows the child — that is the "it still acts like a frame; select the parent, the parent comes up; select the child, the child comes up" note answered by stock selection, not by a nested editor. The Member layout control moves out of View into this section, since it only means something with members.

4.1 Add member

MEMBERS4 members+
Add member
New Blocka fresh definition, Port view, appended last
Link existing…an occurrence of a definition already on this board

New Block creates a fresh definition in Port view, parented to the stack and indexed last — the same getDefaultBlockProps() path the tool uses, then a reparent. Link existing… creates a Block carrying a chosen definition's definitionId; the linking installer already materialises its body and ports on afterCreate, so the command is a search over allBlocks by title plus one createShapes. No library work is needed for V1.

4.2 On the canvas

In stack mode a member is still a stock shape: plain drag translates it, and the settle pass puts it back into a slot. The slot is decided at the landing from the drop y — the same judge the port rows use (blockPortDropTarget becomes blockMemberDropTarget(parent, members, y) returning { before }), and the same visual grammar: a tinted band and a rule while the card is in flight, nothing else moving until release. Dragging out of the parent leaves the stack through stock onDragShapesOut; dragging a Block in through stock onDragShapesIn inserts it at the pointer's slot instead of at its free position. No new gesture, no hold-to-drag: a press on a member is never a cable, so the port lane's hold rule does not apply here.

5 · So what are rows?

Zach's follow-up — "what does rows on a block mean? different things inside, but those are just children no?" — splits cleanly on whose ports they are:

ThingWhose portsKeep?
Port rows (row 0 heading, 1+ body; if:/elif: bands)The parent's own signature, visually groupedYes — one callable, several bands. Unchanged.
Named method rows (track/block-row-arms, unmerged)A row that owns a header and children of its ownNo — that is a child Block. Members give it back with the full inspector, definition linking and export for free.
MembersEach member's own signatureThis proposal.

The honest answer to "does this solve my rows issue" is: it removes the need for the unmerged named-rows branch, and it leaves port rows alone. If, after members ship, no board still uses a multi-row single signature, port rows can be retired in their own step — but that is a separate observation to make, not a decision to bundle here.

7 · Decisions for you — silence takes the default

D1 · Live stack or one-shot command? Ports are live; the wireframe treats members the same way. Default: live in stack mode, one-shot stays for free mode, and the existing WHY comment is narrowed to free mode rather than deleted.
D2 · Order source? tldraw child index vs a stored memberIds array. Default: the child index — stock, paste-safe, nothing to keep in sync. Say "array" if you want members that are not children (a stack of references) — that is a different feature.
D3 · Width policy on the parent (V1) or per member (V3)? Default: parent-level fill | own now, per-member override later when a mixed stack shows up on a real board.
D4 · Expanded children always Own? This is what protects the shared views.expanded. Default: yes, enforced in the pass and proven by a test. The alternative — an occurrence-local width override that shadows the shared box — is more state for a case your own note says you avoid.
D5 · Non-Block children in a stack? Default: they float free, unlaid-out, so a sticky note beside a member still works. "Refuse" would need a new drag rule and buys nothing.
D6 · track/block-row-arms? Default: leave it unmerged; members subsume named rows. Port rows stay.
D7 · How does a Block enter stack mode? Default: the first Add member from the inspector flips bodyLayout to stack; a Free/Stack toggle sits beside the presets for existing frames. Existing boards never flip on their own.

Zach's answers came back the same morning; this section records what shipped against them. The whole feature is one branch, track/block-members-proposal, on top of the proposal above. 8.1 D1, explained properly: one-shot vs live

One-shot (a command)Live (a constraint)
What happens when you press InsetThe members are arranged once, right now. Then they are ordinary free shapes again.The Block adopts the arrangement as a property. It re-runs after every change.
Drag a member half out of lineIt stays where you dropped it.It snaps back into the column — and takes the slot it landed on.
Add a member, grow one by adding a portNothing else moves; you press Inset again to tidy.The stack re-flows and the parent hugs it.
Where it lives nowFree mode — exactly today's behaviour, untouched.Stack mode — the new toggle. Ports have always worked this way.

The implementation of live is the same shape as auto-fit: subscribe at tldraw's side-effect seam, note the dirty stack, settle once after the operation and never during a pointer gesture, write with history ignored, filter your own writes. memberStack.ts is 254 lines.

8.3 Kanban cards, on dnd-kit

The list reorders exactly as the port list does: a DndContext with a 3px activation distance, the grip as the only handle, no SortableContext, and the drop resolved from live row rects — the moved row goes before the first row whose midpoint is below the pointer. ↑↓ on a grip steps one slot. On the canvas there is no new gesture at all: a plain drag is the reorder, because the settle pass re-takes the order from where the member landed, then snaps it into the column. Dragging out of the Block leaves the stack through stock drag-out; dropping a Block in through stock drag-in makes it a member at the slot it landed on.

8.4 The Type block, and "everything is a div"

The screenshot's Type block is today's TypeAttributeRegion: attributeSource parsed into a foldable presentation — deliberately not a second editable schema. The members model does not replace it yet, but it makes Zach's decomposition expressible: a Code block is already a stack member, so "an attribute block is a Block with a Code member" is something a board can hold today (Own width, since only a Block knows how to absorb Fill). The reusable component he pointed at — the rendered code block behind the attribute list — is the right next extraction; projecting a Type's attributes as a Code member would then be a small follow-up rather than a new primitive.

9 · Deliberately not done

Per-member width (V3) waits for a board that needs a mixed stack. Link existing… was dropped from the Add menu on Zach's call: naming a blank member is the link. The Members list does not edit a child in place ("it still kinda acts like a frame"); a row click selects the member and the inspector follows. Horizontal stacks were not designed. Non-member annotations float visibly rather than hiding (D5 above). A Code member keeps its own width — Fill for non-Blocks needs each shape to own a resize path. Nothing here is a PEP yet; if this lands on main, the Free/Stack fork is the one decision worth a numbered record at merge time.
