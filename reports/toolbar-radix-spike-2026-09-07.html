Spike · evidence for a decision, not a feature

The toolbar, rebuilt on Radix

Zach's pivot question: "tldraw is great for whiteboards, but now we're doing more than a whiteboard." This spike rebuilds one surface — the toolbar — entirely on Radix headless primitives behind the existing components.Toolbar seam, then measures what tldraw's UI layer was doing for free. It rides the same seam as the shipped toolbar; ?toolbar=radix is opt-in and the default build is untouched.

Read: visual and structural parity is reached — identical tokens, paint, slots, focus order, one-Escape dismissal, zero console errors. The one hard loss is the digit keys 1–9: they belong to tldraw's OverflowingToolbar, which a raw Radix Toolbar.Root does not carry — the rebuild drops them (and responsive overflow with them). Letter-shortcut suppression survives, but only because the spike re-implements the editor.menus registration by hand; the naive port that skips it leaks tool switches under an open menu.

What tldraw gave for free — and what it cost to replace

Survived the severing (no hand-work)

  • Theme. The --ss-* tokens live on .tl-container, and components.Toolbar renders inside it — so the rebuilt CSS resolves all 12 tokens in both schemes with no :root re-declaration.
  • Dismissal. One shared @radix-ui/react-dismissable-layer stack (tldraw ships Radix internally); one Escape closes the menu and no more.
  • Roving focus. Radix Toolbar.Root is one Tab stop with arrow-key navigation inside — same as tldraw's TldrawUiToolbar.
  • Tooltips. A bare Tooltip.Root joins the provider tldraw already mounts above every components.* override.
  • Icons. Same @tldraw/assets sprite map, read directly.

Needed hand-work or was lost

  • Digit keys 1–9 — LOST. Owned by OverflowingToolbar, not Toolbar.Root. Restoring them needs a document-level listener that outruns tldraw's shortcut layer (memory: tldraw-toolbar-owns-the-digits).
  • Responsive overflow — LOST. Same component. The rebuild is a fixed flex row; fine at 1440px, no "more tools" collapse.
  • Shortcut suppression — hand-written. editor.menus.addOpenMenu on every Radix overlay, or letter shortcuts fire under the open menu (the naive column).
  • Tool overrides — still borrowed. useTools() is kept so the app's arrow-preset onSelect wrapper survives; severing it is a separate change and the single largest non-linear cost.
  • Wrapper-hung CSS. Popover.Root renders no DOM, so the library divider had to be re-hosted on an explicit span.

Cost of a full "tldraw UI → Radix" migration, extrapolated

This one surface is 970 lines of spike (11 TldrawUi* rendering symbols dropped) for near-parity minus the overflow layer. Scaling that:

Cheap & linearStyle panel, menus, dialogs, context menu — presentational, token-backed, already Radix underneath. Mostly CSS re-hosting like this toolbar's.
The real billOverflowingToolbar's responsive + digit-key layer, the keyboard-shortcut system, editor.menus plumbing, and the tool-override system. These are load-bearing behaviour, not chrome — each is its own project.
Not free either wayEvery overlay must register with editor.menus by hand forever after. That discipline is the recurring tax the migration buys.

If the pivot proceeds, the toolbar's overflow/shortcut layer is the fork worth a docs/peps/ record — it is a genuine architecture decision with a defensible alternative (keep DefaultToolbar purely for its overflow math and Radix-skin everything else). Deferred for now per the spike brief.
