A real design system for the chrome — what to adopt, what you already have

Your framing was one question — "we're operating at way too low a level, I don't want to reinvent the wheel" — but it is two separate problems wearing one coat, and every candidate you named solves at most one of them. This doc separates them, measures where the app actually stands on each, and puts all six candidates against the widgets you actually build: the property rail, the inspector, contextual menus, tablists, dialogs.

Recommendation, in one breath: the two axes get two different answers. Axis 1 — converge app-authored chrome on Base UI, component-by-component as files are touched, never big-bang: it covers every primitive the app uses plus the NumberField Radix lacks, and — measured in a browser, not inferred — its outside-press dismissal survives the exact guard shape that starves Radix's in docs/bugs/000210,33,39. Axis 2 — adopt nothing. The --ss-* token layer already is the design system; the dark/light bugs were palette-derivation math inside it, and none of the four candidates sells that fix without a look that fights the canvas36,37. The reversible default if you do nothing: both libraries stay exactly where they are, new chrome work reaches for Base UI first, and nothing migrates until its file is being edited anyway.
Correction, 2026-09-07 (second pass). The first version of this page claimed Base UI registers its press listeners "capture-phase, unconditionally" and is therefore structurally immune to the docs/bugs/0002 class. An adversarial review pushed back, and re-deriving it from the installed @base-ui/react@1.8.0 source plus a browser probe showed the wording was wrong twice over: the listener group is gated on outsidePress !== false (a default, not an invariant), and the capture listener does not decide anything — it re-arms the decision on the event's own target. The conclusion survives and the mechanism is better than advertised, but the immunity is conditional, not structural, and three guard shapes still defeat it. The corrected argument, with the measurement, is in the Base UI section. Four further numbers were wrong and are fixed; they are called out where they appear.
Two things this doc does not do: touch product code (research only, per the brief), and re-litigate the 2026-09-07 six-domain library audit — it extends that audit's method (adopt where a genuine gap exists: elkjs, dnd-kit, colorjs.io) to the chrome layer.

The two axes

Axis 1 — headless behavior primitives. Focus traps, dismiss-on-outside-press, roving tabindex, keyboard navigation, ARIA wiring, popup positioning. This is what Radix and Base UI are — behavior with zero pixels. SystemSketch already has real, partial adoption of both. The open question on this axis is not "adopt a library" — it is standardize on one of the two you already ship, and write the rule down.

Axis 2 — the visual system. Semantic color roles, scheme invariance, spacing and type scale. This is where every dark/light bug you cited actually lives — and it is a CSS-token-and-palette-math problem, orthogonal to which headless kit you use. Radix and Base UI are both unstyled; adopting either fixes no scheme-invariance bug. Material 3 is the one candidate that bundles an opinionated visual system with components — which is exactly what makes it wrong here (argued in its section, not presupposed). Tailwind is a styling authoring syntax on this axis, not a semantic system: it gives you dark: as a mechanism and leaves the palette semantics — the part that broke — entirely to you20.

Grey pills are candidates researched and not recommended for adoption on that axis; blue are the two live headless kits; green is the shipped token layer. Placement is what each thing is, not a quality ranking.

Base UI vs Radix — the real decision axis 1 converge on Base UI, gradually

@base-ui/react 1.8.0 · MIT · MUI's team incl. Radix co-creator Colm Tuite and Floating UI's authors1,5  ·  radix-ui 1.6.7 · MIT · WorkOS8

Both are headless behavior kits — the thing you were worried about hand-rolling is the thing the app already buys. The question is only which of the two to standardize on, and the evidence now points one way:

  • Coverage is no longer the blocker. Base UI 1.8.0 ships every primitive this app uses — Popover, Dialog, Context Menu (verified live; blog posts claiming it's missing are stale), Tabs, Slider, Toolbar, Menu, Toast — plus Number Field (the drag-scrub already adopted in the inspector worktree), Combobox, Autocomplete, Select, Scroll Area4,5. There is no reverse gap — an earlier draft named Hover Card as the one thing Radix has and Base UI lacks, which was an artifact of searching by Radix's name: Base UI ships it as Preview Card, and the installed 1.8.0 tree carries preview-card/ with docs describing the identical component4.
  • The dismissal architecture is the load-bearing difference — but the honest version is narrower than this page first claimed. Radix's DismissableLayer decides outside-press on a bubble-phase document pointerdown, the listener docs/bugs/0002 proves this app starves at 57 call sites across 26 files on main (the record's headline 60/29 is its count on claude/container-primitive-rebuild, which carries src/uiEditor/)9,33. Base UI's vendored useDismiss registers its press listeners in capture phase — gated on outsidePress !== false, which is the default and which PopoverRoot, MenuRoot and useDialogRoot all leave enabled10. The mechanism that matters, though, is not the phase: the capture handler decides nothing, it re-arms the decision as a one-shot listener on the event's own target (addTargetEventListenerOnce) — below every intervening guard, so no ancestor's stopPropagation can reach it10. That immunity is conditional, not structural, and the measured limits are in the table below.
  • Radix is not dying — but the momentum is real and one-directional. Radix still releases (1.6.7 on 2026-07-24 with a controlled ContextMenu, and 1.7.0-rc prereleases through 2026-07-31)7,8; the abandonment narrative traces to one speculative blog post38. But Base UI has MUI's staffed team, monthly releases, a repo pushed the day this was researched2,6 — and the ecosystem is voting: shadcn/ui made Base UI its default primitive layer in July 2026 (new projects pick it ~2:1)14, and MUI names Base UI its "long-term direction"22. tldraw has its own issue open on this (tldraw/tldraw#7584, "Investigate migrating from Radix UI to Base UI") — but read it for what it is: an investigation opened 2026-01-04 and still open eight months later, with four comments and no linked branch, PR or implementation. It is evidence that tldraw considers the question live, not evidence that the engine is moving12.
  • The migration is bounded but not a rename. Core state props survive (open/onOpenChange); what changes is composition: asChild → render prop at every call site, a mandatory Positioner layer on popup-family components, Overlay→Backdrop, Content→Popup, Tabs Trigger→Tab13. 6 files on main import Radix. Every migration guide independently converges on strangler-fig, not big-bang13,14.
  • Mixed-library nesting: a caution, not a blocker. This page previously cited mui/base-ui#2854 — a Base UI popup inside a Radix Dialog that renders but cannot be clicked — as an open live hazard. That was wrong. The issue was closed as completed on 2025-10-16, and its repro pinned @base-ui-components/react@^1.0.0-beta.3 — a beta of the predecessor package, now deprecated at 1.0.0-rc.0 and superseded by @base-ui/react. It says nothing about 1.8.011. The sequencing rule it motivated still earns its place, on general grounds rather than a tracked bug: two libraries running independent portal, z-index and dismissal stacks against each other is untested ground in this app, and stacking is the classic place it bites. So keep it as prudence with a stated expiry — don't nest one library's popup inside the other's modal layer while both ship, and if a case genuinely wants it, spike that one case rather than treating it as forbidden. Standalone popovers (BtInsertMenu, DraftsControl, ContextualControls) migrate freely; anything hosted by CompareDialog or LocalWorkspace migrates with or after its dialog; ReliableContextMenu last (largest surface, and Radix just shipped the controlled API it leans on)7.

The dismissal claim, executed rather than asserted

Both architectures modelled against seven guard shapes in docs/dismiss_propagation_probe.html, re-run at build time in google-chrome (headless). The Base UI column models useDismiss.mjs:458 (capture listener on document) plus :344 (addTargetEventListenerOnce, which re-arms the decision on the event target). Row B is SystemSketch's actual guard shape: React 18/19 attaches synthetic handlers at the root container, so onPointerDown={(e) => e.stopPropagation()} stops the native event there — which is exactly the capture: 1, bubble: 0 the bug record measured33,39.

Read the last three rows. A capture-phase guard on an intervening ancestor (D), stopImmediatePropagation on the target (F), and a document-capture guard registered before the popup mounts (G) all defeat Base UI too. Base UI's advantage is that it survives shapes B, C and E — and B is the one this codebase actually writes. Counted on main today: zero capture-phase pointerdown guards that call stopPropagation, and two stopImmediatePropagation call sites, neither on a popup path (canvasCamera.ts:101, PrimitiveSearch.tsx:101). So the advantage is real for the tree as it stands, and a future capture-phase guard would silently remove it. That is a discipline the markEventAsHandled sweep buys and a library does not.

One caveat the probe cannot settle: Base UI's Popover defaults to outsidePressEvent: 'intentional' for mouse when not trapping focus, which moves the decision from pointerdown to click. The listeners are capture-registered and target-armed either way, so the shape of the result is unchanged — but a guard on onClick rather than onPointerDown is the one to watch under that mode. Main has 6 such onClick guards across 6 files today; none is on a popup path, and the spike below is where that gets confirmed against real markup.

shadcn/ui axis 1 + styling crib from, never install

MIT · Vercel-sponsored (creator employed there since 2023) · a CLI that copies component source into your repo — not a component library14,16

What it actually is in 2026: codegen over headless primitives + Tailwind + CVA. Two recent facts sharpen the picture: it made Base UI the default primitive layer (July 2026)14, and its Radix track moved to the same radix-ui umbrella package this app already depends on15 — so the app is accidentally compatible with both of shadcn's tracks. Neither helps, because:

  • It cannot be used without Tailwind. No official non-Tailwind path exists (the 2+-year-old discussion asking for one has no maintainer commitment)16; every variant, state and responsive rule in every component is a Tailwind utility string inside a cva() map — including JIT-only constructs (has-[>svg]:px-3, arbitrary-value brackets) with no plain-CSS equivalent to extract17.
  • The pattern minus the stack is what the app already does. "Own the source, wrap a headless primitive, theme via CSS variables" — subtract Tailwind and that is literally the existing practice: thin wrappers over radix-ui, styled by hand-authored CSS against --ss-* tokens. shadcn's :root/.dark variable convention is a less capable version of the multi-host token layer already shipped36.
  • What survives as value: a rendered reference gallery of interaction shapes (Combobox, Command, Sheet) built on the very primitives this app uses — worth reading when designing a new widget, never worth npx shadcn add.

Tailwind CSS axis 2 (authoring only) no — argued from numbers

MIT · Tailwind Labs · a styling authoring syntax — explicitly not behavior (that's their separate Headless UI project) and not a semantic palette19

The real cost, measured against this tree:

  • Migration surface: 56 CSS files / 19,518 lines to port and 1,466 className= call sites across 106 of 162 .tsx files to rewire — against a codebase whose styling is already token-driven and class-organized (14:1 class-vs-inline ratio; this is not the inline-style sprawl Tailwind rescues)20.
  • 62 rules across 15 files are permanently unmigratable — their selector subject is tldraw's own DOM (.tlui-main-toolbar__tools, .tl-text-shape-label, .tlui-input…), markup the app does not render. Tailwind cannot reach the part of the page that is the product20.
  • Preflight is a documented, open hazard against exactly this app's shape. Tailwind's own docs warn the global base reset "is known to conflict with third-party libraries"; the v4 disable mechanism is all-or-nothing, and there are open issues (#17481, #17445, #19114) where disabling it still leaks resets — the precise failure mode (base-style bleed into a mounted third-party canvas) this app cannot risk19.
  • The one cheap true fact: v4's @theme inline could expose the existing --ss-* tokens as utilities without rewriting tokens.css18 — but that is a bridge to a second styling idiom the repo would then carry forever, for marginal gain on greenfield lab panels. And on the axis Zach actually cited: dark: is a selector mechanism, not palette semantics — it would not have prevented any of the three recorded dark/light bugs19,37.

Revisit only if a fully canvas-detached surface someday needs one-off styling at a scale where per-feature CSS is genuinely the bottleneck — and even then, the @theme inline token bridge is the entire scope, not a foothold.

Material Design 3 axis 2 + components no as a system — steal two ideas

Spec by Google (m3.material.io) · implementations are the problem: no maintained first-party React path exists21,22

Three concrete, falsifiable grounds — not a taste dismissal:

  • There is nothing to install. Google's own @material/web is Lit web components in official maintenance mode since June 2024 ("new features and components are no longer planned" — engineers reassigned to the internal Wiz framework)21. MUI implements M2, has left the M3 request open since 2021, and its 2026 roadmap doesn't mention M3 — it names Base UI as the long-term direction22. Adopting M3 from React in 2026 means hand-implementing a spec, which contradicts the premise of the exercise.
  • Its density and direction point away from tool chrome. A 48dp touch-target floor against the 24–28px rows of a Figma-shaped inspector; and the 2025 "M3 Expressive" revision moved the system more decorative — spring physics, shape morphing, "personality"23,24. The chrome of a canvas tool must recede; M3's trajectory is the opposite. (Honest caveats: M3 does ship a density system, its canonical layouts explicitly name "a design tool with an inspector panel," and no public evidence settles whether Google's own dense consoles run M3 — that claim is unverified in both directions23.)
  • Its token architecture is validation, not a purchase. md.ref.* → md.sys.* → md.comp.* is the same raw-values → semantic-roles → component-bindings layering the --ss-* system already has23,36.

The two ideas worth taking, free of the look: (1) the on-* role-pair vocabulary — every surface color carries a paired on-color, which is precisely the rule whose absence produced the accent-on-accent-soft 2.6–4.3:1 bug; encode it in tokens.css naming when that file is next touched23,37. (2) the HCT color science — colorjs.io supports HCT/CAM16 natively, and the theme-appearance-lab already adopted colorjs.io; deriving palette ramps in HCT is the library-grade replacement for the hand-rolled colorFromSwatch math that wrote light-mode chrome into the dark table25,37.

rerun.io reference app

Rust + egui 0.36 + wgpu 30 — egui is written by Rerun's own CTO; the whole viewer is egui-drawn pixels29,30

Confirmed from Cargo.toml and their own docs: every panel — timeline, selection inspector, blueprint tree, context menus, all data views — is an egui-drawing Rust crate under crates/viewer/*. The web viewer is the same binary compiled to WASM executing inside a single <canvas>; the npm packages (@rerun-io/web-viewer-react) are lifecycle shells around that canvas with zero authored DOM chrome29,30,31.

  • What does transfer is the discipline: one typed design-token source (re_ui's design_tokens.ron + color table) feeding one styling layer that owns every pixel of chrome32 — the same one-owner principle as tokens.css's "only file that may hold a chrome colour literal" rule, which egui gets by construction and this app holds with tests/test_theme_tokens.py36. Recommendation

Axis 1 — standardize on Base UI for app-authored chrome, by strangler fig. Written as a standing rule: new chrome reaches for @base-ui/react first; existing Radix call sites migrate when their file is already being edited, never as a sweep; while both libraries ship, don't mount one library's popup inside the other's modal layer without spiking that case first11. Sequencing that falls out of the nesting rule: standalone popovers first (ContextualControls, BtInsertMenu, DraftsControl), the two Dialogs (CompareDialog, LocalWorkspace) as units, ReliableContextMenu last. The inspector worktree's NumberField is already on the right side of this rule.

What that rule now rests on, stated plainly. After the correction, the case for Base UI is: (1) coverage — every primitive this app uses plus NumberField, Combobox and Select, which Radix lacks3,4; (2) ecosystem momentum — a staffed team, monthly releases, shadcn/ui's default2,6,14,22; and (3) a real but conditional dismissal advantage: measured, Base UI survives the guard shape this app actually has, where Radix does not10,39. What it is not is structural immunity — three guard shapes still defeat Base UI, and if any of them ever lands in the tree the advantage evaporates for that call site. Weigh (3) as a tiebreaker that happens to point the same way as (1) and (2), not as the reason on its own.

Axis 2 — keep the token layer; harden its two weak seams instead of replacing it. (1) Adopt the on-* role-pair naming from M3's vocabulary next time tokens.css is touched, so "copy on a tint is ink" becomes a name the vocabulary enforces rather than a comment23,37. (2) Move palette derivation (the colorFromSwatch family) onto colorjs.io's HCT, already adopted in the theme-appearance-lab — that is the library-grade wheel for the one part of theming that was genuinely hand-rolled and genuinely broke25,37.

Independent of both, and load-bearing on its own: land the docs/bugs/0002 sweep (stopPropagation → editor.markEventAsHandled: 57 sites across 26 files on main, 60 / 29 on claude/container-primitive-rebuild) with its regression test regardless of library choice. tldraw ships Radix internally for its own menus, so its bubble-phase dismissal stays on the page forever — full app-side convergence on Base UI does not retire the bug class, it only removes the app's own popovers from it33,35.

The reversible default (what happens if you say nothing)

Both libraries stay in package.json. Nothing migrates. The only change is the rule of thumb for new work — Base UI first — which any single future decision can reverse at the cost of zero migrated files. Each component migration, when it happens, is one file and one commit, individually revertable; radix-ui leaves the manifest only when its last importer does, if ever.

The concrete next step (if you want to act)

Spike ContextualControls.tsx — the property-rail popover — from @radix-ui/react-popover to Base UI Popover. It is the sharpest possible test: it lives against the canvas, it sits in the middle of the panel-guards bug class, and it already has a journey (npm run test:contextual-composition). Acceptance is the mechanism, not the symptom: with a stopPropagation guard deliberately in place, assert the popover dismisses and that it did so through Base UI's target-armed press path rather than the focusin side-channel that currently hides the Radix bug — the check docs/bugs/0002 says no journey makes today10,33. The probe below tells you what a passing run should look like; the spike is what proves it survives contact with a real portal, a real canvas and a real tldraw layer stack, which no synthetic probe can. If it holds, the standing rule is validated end to end; if it doesn't, one file reverts and the rule flips back to Radix-first at zero cost.

MUI (Foxglove's substrate) A second visual language and a second component substrate beside tldraw's. The thing worth having from Foxglove — the schema-driven settings tree — the app already independently built. Note the argument that was withdrawn: MUI 9.4's nativeColor mode can alias live host CSS variables, so "JS-time theming can't follow the host" is no longer a reason to rule it out26,27,34,36,40.
A big-bang Radix→Base UI sweep The transition is the risky part, not the endpoints: two libraries running independent portal/z-index/dismissal stacks is untested ground here, and the asChild→render rewrite deserves per-file review, not a batch diff. Strangler fig gets the same destination without the exposure. (The specific bug once cited for this, #2854, is closed and was filed against the deprecated pre-1.0 package — the caution is general, not tracked11,13.)
Porting tldraw-owned chrome to either library The toolbar spike already priced this: near-parity costs 970 lines and loses the digit keys and responsive overflow that tldraw's OverflowingToolbar owns; every overlay then pays the editor.menus registration tax forever. The stock boundary stays where it is35.
