A port is one line of code

Refactor + the general code text box + the lane prototype · 2026-09-09 · measured against 51a4e674 · tldraw 5.3.2 pinned, CodeMirror view ^6.38.6 · the thinking · the evidence · the lane prototype · what needs you

What shipped. Every place a port is edited is now one text field spelled name: Type = default: the docked inspector row (was Name · Type · Default, three boxes), the on-canvas click-to-edit editor (was a name box or a type box depending on which span you hit), and the free Port's panel (was Name · Type · Value). Underneath them is a new general component, CodeField — a single line of CodeMirror that knows nothing about grammar until one is plugged in — and one grammar module, portSignature.ts, that is the entire "language service": it splits the line into its three roles for highlighting, tells the completion which slot the caret is in, and writes the stored triple. Storage did not change. The stored { name, type, defaultValue } is the parse tree of the line; the field formats it in and parses it back on every keystroke, so the Block paints the name, the type hint and the = 5 chip live while you type, and every binding, projection and journey that reads the triple keeps reading it.

Loss of nothing, checked. The one thing three boxes had that one line could have lost was the parametric default — live Python evaluation, wavy underlines on undefined names, "Variables used here". It moved onto the = slot of the line instead: the same debounced evaluation runs on exactly the text after the equals sign, squiggles land inside that slot, and the resolved value now rides beside the formula as a ghost (chassis_width / 4 ⇢ 0.105) instead of replacing it. The formula is source text; it stays visible.

The thinking, improved

1 · The field is the port's parse tree, so store the tree

Your instinct — "we can still parse it internally for the Python" — is right, and it decides the storage question. The Type block stores text (attributeSource) because its body is multi-line and a parse would drop comments, docstrings and indentation. A port line has nothing a parse drops: name: Type = default round-trips through the triple losslessly for every name without a depth-0 : or =, and the parser respects brackets and quotes so dict[str, int], Callable[[int], str] = f and lambda x: x all land where they belong. Keeping the triple canonical means no migration, no second copy of one fact, and no consumer changes — the alternative (text canonical, triple derived) would have touched every reader of port.name and created exactly the two-truths trap the members work just avoided. The reversal trigger is written into the module: if the grammar ever grows something the triple can't hold (*args, a trailing comment), add a source field then.

2 · "Code text box" = one component + a grammar, and a grammar is just slots

The general feature you named already existed in four separate pieces — the Code block (CodeMirror, multi-line), the parametric expression field (CodeMirror, one line, evaluation), the Type block's highlighted textarea, and the type-name completion built for the Type babble. What was missing was the abstraction that makes them one thing. It is small: a grammar is a function from (text, caret) to a slot. The slot drives everything — which mark to paint, which completion source to consult, whether to stay silent. That is why "as soon as you enter a : it knows you are doing a type" needs no parser generator: portSignatureSlotAt is thirty lines and is shared by the highlighter and the completer, so they can never disagree.

v1 · plain

<CodeField extensions={[]} />

A text box with a real caret, IME, undo, paste — CodeMirror's, not a mirror div. No grammar. This is already the same component; nothing to build later.

v2 · grammar-aware shipped

portSignatureExtensions(…)

Slot marks (name / punct / type / default), completion dispatched by slot, diagnostics scoped to a slot, a ghost value. Ports and the free Port use it today.

next · more grammars

Type attribute lines, Type Mapping aliases (Name = expr), the parametric expression field itself.

Each is a new slotAt + extensions, not a new editor. The expression field should become CodeField + an expression grammar.

4 · Where this sits against the whiteboard rule

"The whiteboard stays dumb, Python is rigid" holds. The TypeScript parser is the shell only — it finds a depth-0 colon and a depth-0 equals sign and nothing else; what is inside the type or the default is opaque text until the Python side reads it. Free text is a name, always: temperature sensor readings is a legal port and nothing lints it. The completions offer, they never validate. The one place a red mark appears is the default slot, and that is Python's verdict (the existing expression host), not the board's.

6 · One trap worth recording

Enter closed the canvas editor and then re-opened it on the title. The keydown that CodeMirror consumed kept bubbling to tldraw's document listener, where Enter on a selected shape starts editing it — stock behaviour, correct, and invisible until the field it was landing on stopped stopping propagation. The old <input> did stopPropagation(); the field now handles Enter and Escape on the raw DOM event so it can do the same. A keymap binding cannot, because it never sees the event.

Multi-line port editor · one line per port (on by default; Settings › Canvas › Port editor)

Built the same afternoon from your follow-up, then promoted to the default at your call ("for people used to working in an IDE this feels natural and fast"): instead of one line per field, each lane of a Port view is one multi-line code text box — the inputs lane on the left, the outputs lane parked just outside the right edge so it is typed left-to-right — and each line is a port. Clicking the left half of the Block opens the inputs lane with the caret on the row you clicked; the right half opens the outputs. Because the lane is a CodeMirror document, the IDE keys come for free and mean what you'd hope: Alt+↑/↓ or Ctrl+↑/↓ reorders a port, Enter adds one on the next line, Shift+Alt+↓ duplicates one, Ctrl+Enter commits, Esc leaves. Every keystroke reads the whole lane back into the same port records: reconcilePortLane diffs the lines, a line that still says what a port said keeps that port's id (so a moved port keeps its cables), a line edited in place keeps its id, a new line is a new port, a missing line is a removed one. Storage is still the triple; header ports and hidden ports are not lines and keep their place around the lane.

What the lane taught about the overlay idea. The Block itself is the rendered layer: while the lane is open the Block keeps painting dots, chips and labels from the store, so you are looking at source and projection at once, aligned row for row. That is the two-state field you described — rendered by default, source when you click in — with the cursor landing on the right line because the lines are the rows. What is still missing is the reveal rule inside the editor (raw only on the caret's line, rendered elsewhere); here the whole lane is raw while open, which is the "switch the whole thing" mode. The per-line reveal is the next step and is a decoration rule, not a second editor.

Two questions you asked, five directions each

A · the outputs lane "feels reverse". Typing into a right-anchored box is nothing anyone's hands know. The five ways out, with the one you suggested already applied:

A1 · Park it outside, type it normally applied

Why: Rows still map one-to-one to the dots; the hands type left-to-right; the Block keeps painting the real labels underneath. Your own suggestion.

Cost: The mirror symmetry of the painted labels is lost while the lane is open; the editor can overlap whatever sits right of the Block.

A2 · Right-aligned, in place (the first cut)

Why: Perfect correspondence with the painted labels: the raw line sits exactly where the rendered one was.

Cost: The caret lives at the right edge and text grows leftward — this is the part that feels reverse. Rejected by driving it.

A3 · Mirrored grammar for outputs

Why: What the labels already paint (type then name, toward the socket) becomes what you type, so the mirror is honest.

Cost: A second grammar to learn and to parse; Python never spells an output this way. Not recommended.

A4 · Both lanes at once, both outside

Why: The Block becomes the rendered view and the two lanes its source, side by side — the overlay picture literally.

Cost: Twice the surface for an edit that almost always touches one side; hides nothing but crowds the canvas. Not recommended.

A5 · One signature strip under the Block

Why: It is the Python: one line, inputs then outputs, the arrow between them. Reads like the code it will become.

Cost: Loses the one-line-per-port correspondence with the dots, which is the whole point of the lane; better as the Code-block view of a Block than as its port editor.

B · what the text box does with width. A lane is a column of one-liners; the question is what happens when a line is longer than its half of the Block, and whether the box should own more space while it is open.

B1 · Run off into the page applied

Why: Nothing moves under your hands: no horizontal scroll, no ellipsis chasing the caret. The painted label clips as it always did once you leave.

Cost: A very long default can cross a neighbour on a busy board while the lane is open. Acceptable for a one-line grammar; that is what B5 is for.

B2 · Clip at the wall, scroll to the caret

Why: The Block never grows and nothing leaks over the canvas.

Cost: Sliding text is the frustrating case you named; you lose the start of the line the moment you type the end.

B3 · The Block grows while editing

Why: Everything stays inside the Block and readable.

Cost: Layout thrash on every keystroke and cables re-route as the wall moves; the Block's width is a stored property you did not ask to change.

B4 · Both lanes activate, both park outside

Why: The width question disappears: the lanes are outside, the Block is pure render.

Cost: Same as A4 — the second lane is noise for a one-sided edit.

B5 · A ⤢ button opens a bigger viewer

Why: Long definitions get room without the Block changing; wrapping is fine there because the modal is not row-aligned. The same two documents, so nothing to sync.

Cost: One more surface to build; the modal is where the per-line reveal would first be worth doing. The natural next step.

Recommendation, and what silence keeps. A1 + B1 are live now: the outputs lane parks outside the right edge and types normally; while editing, a long line runs off into the page rather than scrolling or clipping, exactly as you reasoned ("it runs off into the page … if it must be one line"), and the painted label clips as it always did. B5's ⤢ button is built: it opens the lane you are in — one document, wrapped, with room — in a modal inside the theme root; the two-lane side-by-side form in the mock stays a mock. A4 (both lanes at once, outside) is the one I would not do: it doubles the surface for a rare case and hides the Block's own render, which is the thing the lane is supposed to sit beside.

Rough edges, deliberately left

  • Rows and branches are not lines yet. A moved port keeps its own row/branch; a new port takes its neighbour's. The Sep 5 port-text babble's --- divider is the obvious grammar for a row break, and a lane with several rows will not line up with the row gaps until it exists.
  • Header ports (row 0) and hidden ports are outside the lane — visible in the Block, not in the text.
  • Line pitch is measured from the first two dots; a Block whose rows have already been compressed to fit re-measures on every render, so the editor keeps up, but the outputs lane in Aligned layout shares rows with the inputs and inherits their pitch.
  • The inspector still lists ports one field per row. The lane could replace the list there too; not done.
  • Per-line reveal is width-only so far: folding long lines to … is the reveal rule applied to length; rendering chrome (chips, dots) inside the lane on inactive lines is the next step.
