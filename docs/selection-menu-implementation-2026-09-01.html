SystemSketch · implementation report · 2026-09-01

The selection menu now behaves like FigJam's

One dark pill, centred on the selection and 16 px clear of its overlay, flipping below when there is no room above, clamped to a safe area that treats the bottom tool belt as an obstacle, the same size at every zoom, and out of the document entirely while you drag or resize. The behaviour spec was measured from the running FigJam editor; this is what shipped against it, and the proof that it did.

9/9 browser checks 13 placement unit tests product composition · 1440 × 960 tldraw 5.3.2, unforked

1 · What was wrong

Four separate defects, three of them in tldraw's TldrawUiContextualToolbar's policy and one of them mine. The first is the one that produced the reported symptom.

The menu never moved

It sat at the container's origin, on top of the document title, and answered clicks meant for it.

SelectionMiniMenu mounts while the marquee is still down — brushing selects as it goes — and the new component returned null during a manipulation. Its position reactor therefore executed once with ref.current === null, subscribed to no signals, and its scheduler never fired again. From outside this is indistinguishable from an early return: data-side null, no inline style, ever.

Now

The gate moved up into a wrapper. PositionedSelectionMenu — which owns the ref, the ResizeObserver and the reactor — only mounts when its element is guaranteed to exist, and the reactor reads every signal before it touches the DOM so an early bail cannot unsubscribe it.

A hidden menu still answered hit tests

Invisible, but elementFromPoint at its centre resolved to one of its buttons.

opacity: 0; pointer-events: none on the container is not enough, because .tlui-button re-enables pointer events for itself and a container rule cannot undo that.

Now

The same descendant pair tldraw uses for its own contextual toolbar: pointer events off for the menu and everything inside it, back on only under [data-visible='true'].

Near the top edge the toolbar landed on the shape

tldraw's primitive clamps the vertical position; it has no flip.

y = clamp(y, 16, vsb.h - h - 16) in TldrawUiContextualToolbar.getToolbarScreenPosition. Its gap (8) and margin (16) are module constants with no prop.

Now

Placement is now SystemSketch's own pure function, and the flip is one branch in it.

The menu rode along through drags and resizes

It followed the shape for the whole gesture instead of getting out of the way.

The primitive hides during manipulation only when handed an isMousingDown prop, which nothing supplied.

Now

The select tool's own state path is the signal: Editor.isIn('select.translating') and its six siblings. That also covers handle drags, rotation and cropping, which a pointer-down flag would have missed.

A reactor that runs once against a missing element is invisible from outside. Measuring the DOM showed data-side null and no inline style, which reads exactly like an early return that latched. It was not: the reactor had subscribed to zero signals and could never fire again. That is why the fix is structural — the element's existence is now a precondition of the component that owns the reactor, not something the reactor has to check.

2 · Why the primitive was replaced rather than configured

tldraw's contextual toolbar already implements most of this specification, and SystemSketch used it. Its policy, though, is four module-scope constants with no prop and no override; two of them differ from FigJam's and one behaviour — the flip — does not exist in it at all. 

// node_modules/tldraw/…/primitives/TldrawUiContextualToolbar.js
const TOOLBAR_GAP   = 8       // FigJam: 16, from the overlay
const SCREEN_MARGIN = 16      // FigJam: 20
// …and the placement itself, which clamps where FigJam flips:
y = clamp(y, SCREEN_MARGIN, vsb.h - toolbarBounds.h - SCREEN_MARGIN)

The one supported lever is getSelectionBounds, and it is genuinely enough — you can invert the primitive's own formula and hand it a synthetic rectangle that lands the toolbar wherever you like. That was rejected: it would make SystemSketch's placement silently depend on a private constant, so a tldraw upgrade that changed TOOLBAR_GAP would move our menu with no failing test and no diff. Owning 132 lines of placement is cheaper than owning that coupling.

Everything except the policy is still stock, and none of it is reached through a fork: useQuickReactor for the per-frame write, TldrawUiToolbar for the toolbar semantics, usePassThroughWheelEvents so a scroll over the menu still pans the canvas, markEventAsHandled on pointer-down, and InFrontOfTheCanvas as the mount point. The coordinate conversion is the one tldraw documents for overlays — screen point minus the viewport's screen position — which is also what the primitive does internally. 

// src/chrome/selectionMenuPlacement.ts — the whole policy
let side = 'above'
let y = overlayTop - menu.h - SELECTION_MENU_GAP
if (y < SELECTION_MENU_MARGIN) { side = 'below'; y = overlayBottom + SELECTION_MENU_GAP }

const x = clamp(centreX - menu.w / 2,
                SELECTION_MENU_MARGIN,
                viewport.w - menu.w - SELECTION_MENU_MARGIN)
y = clamp(y, SELECTION_MENU_MARGIN, floor - SELECTION_MENU_MARGIN - menu.h)

One constant was re-measured rather than copied. FigJam reads as 40 px above a shape because it paints mid-edge grab dots about 20 px outside the box and leaves its 16 px gap above those. tldraw paints handles on the corners instead, and a selected 240×140 rectangle at (700, 380) paints selection blue from (695, 375) to (944, 524) — a 5 px stand-off. Copying 40 would have looked wrong; copying the rule and measuring the local overlay gives 21 px from the box and the same 16 px from the chrome.

5 · Deliberately not FigJam

One documented delta from the spec is unimplemented, on purpose.

Spec saysSystemSketch doesStatus
FigJam carries no destructive command in the pill. Copy, Delete, z-order and Lock live in the right-click menu, where a mis-click is not fatal. The pill carries Delete — on the plain-selection branch always, on the Block branch only for a batch. Open, and Zach's to call. It is a conflict between two reference apps rather than a defect: this placement work was specified from FigJam, while the batch-editing work next to it was specified from Excalidraw, which does put Delete in the selection pill.
It is one decision covering three cases, not a Block-pill detail. Delete is reachable from the plain-selection pill for one shape or many (SystemSketchChrome.tsx, the N selected · Inspect · Delete branch), and from the Block pill only when several Blocks are selected — EditorBlockSelectionMiniMenu passes onDelete on its batch branch and not on its single-Block branch. So today, selecting one rectangle offers Delete and selecting one Block does not, at the same pill position under the same gesture. Whichever way the reference-app question is settled, settling it should make those three cases agree; changing one of them alone would trade a spec deviation for an inconsistency users can feel.

tests/block_batch_editing_smoke.mjs asserts the batch pill exposes Delete, but that assertion records the existing behaviour rather than requiring it — it is not the reason the button is still there, and it follows the product call rather than setting it.

Reproduce. npm run test:selection-menu for the browser proof and its frames; npm run check for types, the 13 placement unit tests, and the Python suite. Rebuild this page with python3 docs/build_selection_menu_implementation.py.

Scope. Verified in the full product composition at 1440×960 and at 1680×857. The placement constants were not re-checked at other device pixel ratios, and the tool-belt floor is resolved by querying .tlui-layout__bottom__main — a stock tldraw layout class, but a class rather than an API.
