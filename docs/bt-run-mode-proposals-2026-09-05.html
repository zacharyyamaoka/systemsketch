Phase 1 of turning the runtime lab into the real feature: five genuinely different places the mock run could start from, each drawn onto captures of the actual app chrome (not invented UI), scored against explicit criteria, one recommendation — runner-ups kept visible per house convention. 01P1 · ▶ Run on the selection pill — Zach's suggestion

  • Lives exactly where Tree/Process already lives — the surface Zach flips most, so discovery is immediate on selection.
  • Zero at-rest chrome: nothing appears until a region is selected (B11-clean).
  • The pill is command-backed (behaviorTreeCommands), so pill and inspector cannot disagree.
  • Transient surface — the pill hides on deselect, so the RUNNING transport cannot live here; needs a docked strip once running.
  • The pill is one group away from crowded.

02P2 · ▶ on the region's own header band

  • Per-region and always visible: the run affordance sits on the thing that runs, selection or not.
  • Matches Flowstate's mental model (execution controls belong to the process card).
  • At-rest chrome tax on every region on every board — the exact thing atlas B11 warns about.
  • Small target at typical zoom; competes with title/subtitle space, and the header already carries the error count.

03P3 · a Run section in the Behavior Tree inspector

  • Room: presets, seed, speed and the transitions table all fit; nothing else in the app has this much space.
  • Config-beside-source: mock parameters are authored in the same panel (Phase 2's Node section).
  • Lowest discoverability of the five — behind select-then-dock; nothing on the canvas hints a tree can run.
  • As the ONLY trigger it hides the feature; as the detail surface it is exactly right.

04P4 · a Flowstate-style transport strip docked on the region

  • The reference behavior, verbatim — Flowstate docks play/stop/step above the root; zero relearning for anyone who has seen it.
  • The transport is exactly where the eyes are during a run; scrubbing happens next to the paint it drives.
  • As the TRIGGER it must exist before any run is attached — a floating strip at rest violates B11 (Flowstate only shows it because execution is always attachable there).
  • Floating chrome over the canvas; must dodge the Start pill, insert buttons and marching cables.

05P5 · Run as a third projection (Tree · Process · Run)

  • Reuses the strongest muscle memory in the feature (the projection flip).
  • Conflates a lens with a mode. The runtime state model was built so one status map paints EVERY projection — you should watch a run in Tree or Process at will; making Run a sibling of those forbids exactly that.
  • Worst of the five on distinct-from-editing: it looks like one more view flip, the opposite of “this is a live run, your document is safe.”
  • A projection is authored presentation persisted in props; a run is ephemeral. Storing “projection: run” would write runtime state into the document.

07Phase 2 · the per-node mock-parameter model

Zach's brief, verbatim: “each node should have the option to define its own success chance, or expected execution time”, presets stay as bulk moves, values must survive “when you make new trees using the same nodes,” and outcomes are randomized around the authored expectation.

Where the values live — the document's own skill registry

The app already has exactly one place where a skill exists independently of any occurrence in a tree: the <TreeNodesModel> declaration (btcppXml.ts parses it into BtNodeModel; the Behaviors panel and the inspector Library are both derived from it). Mock parameters are therefore authored per skill, on the model entry — underscore-prefixed attributes, BT.CPP's own convention for non-port metadata (isReservedAttribute already treats _… as reserved, so they can never be mistaken for ports):

<TreeNodesModel>
  <Action ID="command_multi_axis_gripper" _mock_success="0.55" _mock_duration_ms="800">
    <input_port name="gripper"/>
  </Action>
</TreeNodesModel>
  • Survives reuse: every tree in the document (subtrees included) that uses the skill reads the same profile — Zach's “sense of what you can do” when composing new trees from known nodes. (Cross-board reuse is out of scope, same as the skill declarations themselves; noted, not hidden.)
  • It's authored data, so it belongs in the document — editing it goes through a command (setBehaviorTreeMockParams), is one undo step, autosaves, and round-trips through BT.CPP tooling that ignores unknown reserved attributes.
  • Runtime status never touches the document — the run itself lives in an ephemeral module store (the recorder-store pattern), exactly as the runtime-viz proposal specified.

Defaults, presets, sampling

  • Defaults: an undeclared skill mocks at 90% success, 800 ms; conditions at 95%, 120 ms — a fresh tree runs reasonably with zero configuration. Builtins keep their semantics (AlwaysFailure fails, Sleep sleeps its msec, decorators decorate).
  • Presets are bulk setters of the authored values, not a runtime mode: Nominal writes success 1.0 for every skill the tree uses; Flaky multiplies each current success by 0.6 (floor 0.35); Chaos writes 0.6 everywhere. One command, one undo step — and afterward the per-node values ARE what the preset wrote, visible and individually editable.
  • Sampling: at run time each leaf's completion draws duration ~ U[0.7·d, 1.3·d] (per attempt) and outcome ~ Bernoulli(success) from a seeded RNG — a node at 80% succeeds in roughly 80% of runs, never always. Seed shown in the Run section; same seed, same run.

08What Phase 3 implemented — same day, proven in the real app

  • src/behaviorTree/runtime/: mockParams.ts (authored profile read/write, defaults, presets as bulk writers), btMockEngine.ts (BT.CPP semantics — latched/reactive/memory sequences and fallbacks, Parallel/ParallelAll thresholds, IfThenElse/WhileDoElse, the decorator set incl. RunOnce and SequenceWithMemory persistence, SubTree descent, loud refusal for Switch/ManualSelector — emitting the canonical transition log, with per-tick snapshots kept only as the oracle tests verify the fold against), runStore.ts (recorder-store pattern: ephemeral, never the document; XML drift stops a run as stale), BtRunOverlay.tsx (node paint + spinner + mode frame + the docked transport strip, camera-tracked in the chrome's front layer).
  • The P1 trigger (bt-pill-run on the selection pill), the P4 strip while a run exists, the P3 Run section (presets · seed · speed · the Groot2 Transitions table with filter, row highlight, «/» transition stepping), the Mock rows in the Node section, and the purple mode frame + MOCK RUN tag.
  • One deviation from the lab, found by looking: the lab's mix-blend-mode: multiply fills render opaque in the app's transformed front layer (an isolated stacking context — the blend can't reach the canvas) and erased card text. The overlay now uses low-alpha veils solved to composite to the EXACT sampled swatches over a white card (rgba(74,18,236,.16) → #E2D9FC, etc.), keeping the card text readable. All run colours are --ss-run-* tokens in src/theme/tokens.css — the theme gate caught the literals.
  • Tests: 19 vitest cases (btMockEngine.test.ts — semantics, every-tick fold≡snapshot across seeds, the ancestors-running invariant, 30%-node statistics over 600 runs, replay determinism, params/presets round-trip) and the 32-check CDP journey tests/behavior_tree_run_mode_smoke.mjs (npm run test:bt-run), plus npm run check green: 1482 vitest · 118 Python incl. the theme gate.
