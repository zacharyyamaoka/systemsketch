SystemSketch · design review · 1 September 2026 · answers “Recording program state”

Record the last 30 seconds

Your brief is right about the shape — a slow filmstrip and a fast text stream on one clock, handed to an agent as prose plus file paths. Two changes make it land: the button should save what just happened, not start a take (you wrote that rule yourself in July 2025, for the robot logger), and the pixels should come from Chrome's own screencast over the debugging port, not from inside the page. Both halves were run in the real app before this page was written: the fast channel cost the app 2.1 ms over 8.4 s, and Chrome delivered 99 frames with the inspector, the menus and the handles in them.

1 · Upgrades to the brief

Seven places where the note's framing can be sharpened. Each one changes something concrete in the build.

1“Start recording” is the wrong verb

By the time you notice a bug, it has happened. A recorder you have to start captures only bugs you can reproduce on demand — the easy ones. Keep a rolling buffer of the last N seconds always (the fast channel costs 0.03 %), and make the primary button Save the last 30 s. Keep an explicit Record next ≤ 30 s for the reproducible case; that is the one with the red bar at the top. NVIDIA, Xbox, PS5, Steam and Jam.dev all landed here, and so did your bam_logger note: “you can only save data retrospectively if you have already recorded it.”

2Two consumers, two channels

The agent reads files — JPEGs with its Read tool, JSON lines it can grep. You watch a scrub bar. Your own Match-Mismatch decision from July: layout is spatial → image; behaviour is causal → text. So the recording is a folder first, and the viewer (§3) is a view over that folder, never a separate format. Never base64 into the clipboard — the copy-for-claude template already learned that.

3“State” has four parts here

tldraw's store (document and session: selection, hover, editing, camera are ordinary records), the state chart path (select.pointing_block_port → select.dragging_handle), the open menus, and the raw input. The spike's state lane read like a narrative of the interaction — and it exposed a bug in the spike's own script (§3). Store diffs plus the t=0 snapshot also make the recording replayable: loadStoreSnapshot then applyDiff per row.

4Pixels come from outside the page

The bugs you chase are in the UI chrome — the selection menu, the inspector, port handles — and tldraw v5 paints handles and overlays to a <canvas>. editor.toImage() shows shapes only, and tab self-capture needs a picker dialog. Chrome's Page.startScreencast shows exactly what you saw, sends a frame only when the page repaints, and costs the page nothing. The price is one flag on the desktop launcher.

5One clock, and draw the cursor from data

Screencast frames carry Chrome's swap time; the text rows carry performance.now(). Both are wall-clock on one machine — the spike measured a median skew of 7 ms. No frame source includes the mouse pointer, so the viewer draws it from the input lane, the way Playwright's viewer draws the click dot.

6The cap is a budget, not a safety net

30 s at the measured rate is ≈ 357 frames · 17.4 MB raw, and up to 88 MB if you drag continuously. An agent will not read 300 screenshots. So the cap does two jobs: bound disk and jank, and bound what the agent must read — keep one frame per 300 ms (≤ 100 frames, ≈ 4.9 MB per 30 s), all of them on state changes anyway because Chrome only paints on change. Adjustable 5–120 s in the Dev menu, never unlimited.

7A recording should be able to become a test

The input lane is a list of Input.dispatchMouseEvent calls with timestamps; the harness already speaks that. Replay it at the recorded viewport onto start.snapshot.json and a bug report becomes a failing tests/*_smoke.mjs. Not v1 — but it is why the folder must carry the viewport, the snapshot and screen-space coordinates from day one. It also answers your daily-note thought that recordings double as goldens.

2 · The shape: two channels, one clock, one folder

Everything on the left is public tldraw API and existing seams in this repo. Everything on the right is the Python host you already have plus a small Node sidecar. The single new dependency is a Chrome flag.

What the lane told me that the screenshots did not

The spike caught its own bug. Step 6 of the script was “press on the detector and drag it 180 px”. The detector never moved: the state lane shows pointing_shape → editing_shape with trigger double_click at +5.16 s — my press landed inside tldraw's double-click window after the selecting click, so the gesture became “edit the title”, and there is no select.translating anywhere in the run (0 occurrences). That is the feature working: the explanation was in the text, and an agent would have read it in one grep.
Keys are only half-visible from the editor bus. Enter and Escape show up as key_up (3) and never as key_down (0): while a text editor or a menu has focus, the key-down is consumed before tldraw's document handler sees it. The product recorder therefore needs a thin DOM lane — capture-phase keydown/pointerdown on window — beside the editor lane. Cheap, and it is exactly the class of fact the design would have got wrong on paper.
Zero jank. 2.1 ms inside the recorder over 8.4 s, with every pointer move and every store diff summarised. Always-on is affordable.

5 · Where the pixels come from — criteria, then options

The text channel has one answer (tldraw's public seams). The pixel channel has five candidates. Weighted for your situation: a Desktop Chrome window you launch yourself, an agent as the first reader, and a stock-tldraw rule.

#CriterionWeight
C1Shows what Zach saw — tldraw UI chrome, menus, inspector, handles included×5
C2One click, no dialog, in the Desktop window and in a plain browser tab×4
C3Agent-readable output: image files + text an agent can Read×5
C4Off-the-shelf; tldraw stays stock; the missing piece is small×4
C5Retroactive: can hand over the last 30 s, not the next×3
C6Does not perturb the interaction being recorded (no jank)×4
C7Playback for a human (scrub, watch)×2

Recommendation

A — CDP screencast sidecar, with D as the fallback when the channel's Chrome has no debugging port (a plain browser tab): text lanes still record, frames come from editor.toImage() and the packet says so (“canvas-only frames”). C (rrweb) is the right answer for a human-first replay product and the wrong one here: its output is not files an agent reads, and tldraw's canvas overlays are outside the DOM it records. B requires a picker or a test-only flag and puts a video encoder inside the page you are trying to debug.

Chrome ≥ 136 refuses --remote-debugging-port on the default profile; the desktop launcher already uses its own --user-data-dir per channel, so the flag is legal there.

6 · What it looks like in the Dev menu

Left: your screenshot of the Dev panel today. Right: the proposed “Recording” section rendered in the panel's own row grammar (glyph · label + detail · action), placed between “Isolated presets” and “Version & updates”. Window chips replace a free-text field so the cap can never be unset.

On Stop: a one-line “what went wrong?” prompt, skippable — its text becomes the first line of the packet and a mark row on the timeline. The clipboard write happens on that click (a user gesture, so it is allowed); if it fails, the row says so instead of pretending, and “Copy last recording” is the retry. The auto-stop at the cap has no gesture, so it saves the folder and lights the Copy row rather than touching the clipboard.

7 · How to build it — seams, in order

Everything plugs into a seam that already exists. The stock-boundary test keeps passing because nothing new is bolted beside the engine: one more install*(editor) in onMount, rows in a panel that is already ours, a route in a host that is already ours.

  1. src/recorder/flightRecorder.ts — the ring buffer (v1)The spike's in-page code as a module: six lanes plus the DOM lane, performance.now() clock, a window of N seconds trimmed on every push, getStoreSnapshot('all') taken when a save starts and kept from N seconds ago (snapshot at the buffer's tail, so a retroactive save can still replay). Installed from onMount under import.meta.env.DEV or a ?recorder=1 flag, like installDevelopmentSeam. Always armed; cost measured at 0.03 %.
  2. Dev menu rows + REC bar (v1)In SystemSketchUtilities.tsx, a “Recording” section in the preset-row grammar; window chips persisted at systemsketch.recorder.window-s.v1; the bar as a small component rendered by SystemSketchSurfaceHost only while an explicit take runs. No new tldraw component seam — NavigationPanel and InFrontOfTheCanvas are already claimed and asserted.
  3. scripts/server.py — POST /api/recordings, GET /api/recordings/last (v1)Body: header, rows, snapshot, optional canvas-only frames. Writes ~/SystemSketch/recordings/<ISO>-<slug>/ under files_root (jailed like boards), staged then os.replaced like a release, keeps the last 20, returns {path, packet}. Add to the POST allow-list; remember controller_fingerprint covers server.py, so Preview's API pair restarts on next launch.
  4. scripts/recorder_frames.mjs + one launcher flag (v1)--remote-debugging-port=<4324 for Preview, 4325 for Stable> appended in open_app(); the host spawns the sidecar per channel, which attaches to the page whose URL matches the channel, runs Page.startScreencast into a ring buffer, and on /api/recordings writes the last N seconds at one frame per 300 ms into the same folder. ~120 lines; the spike is its first draft.
  5. Proof (v1)tests/recorder_smoke.mjs: Save-the-last-30-s after a scripted gesture → folder exists, packet on the clipboard (read back with Browser.grantPermissions clipboardRead), frame count within the cap, a key_down present in the DOM lane. Plus docs/build_recorder_implementation.py and a README paragraph.
  6. playback.html per recording + state→source map (v2)The viewer above, templated by the host into each folder. The packet gains a section mapping each state-chart node seen to the file that defines it (grep the state ids under src/ at save time), so the agent's first Read is the right file.
  7. Replay-to-test and a Chrome trace export (v3)Turn a recording's input lane into a failing journey against start.snapshot.json at the recorded viewport; and emit trace.json with legacy Screenshot events + extensibility marks so DevTools › Performance › Load profile is a second, free viewer. Both unverified today, deliberately parked.
