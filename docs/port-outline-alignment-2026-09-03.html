The port socket that went missing

tldraw's selection/hover outline is computed independently of the live port dot it is supposed to trace. One view's ports had drifted out of it entirely. Fixed, and now pixel-checked on every primitive that carries a port. 2026-09-03.

174/174alignment checks pass, across every Block view, Branch and Loop control/header ports, a 12-port stress case, a resize matrix, and extra zoom levels

1 · What was actually wrong

The blue trace is not part of the live DOM paint at all — since tldraw v5 the selection/hover indicator is stroked to an overlay <canvas>, computed by each shape's getIndicatorPath(shape) from shape.props alone. The port dot itself is an ordinary .Port div, positioned by the same layoutBlock coordinates and centred with a CSS box-shadow ring — which is why a coordinate-math bug in that path would show as a shift, not what the screenshot actually showed: a straight line cutting clean through a dot that was otherwise sitting exactly where it should.

The reason turned out to be a missing case, not a wrong number. Simple Block's ports are subtle — invisible until the canvas is hovered, so the header stays uncluttered — and getIndicatorPath read that flag as "this port doesn't exist" and skipped it. The dot's position was always correct; there was simply no socket cut into the outline for it to sit inside of, so the outline's straight body edge painted straight over it the moment hover revealed the dot.

2 · The fix

subtle only ever gated the dot's paint opacity in CSS — it was never a signal that the port itself doesn't exist. The fix removes the skip, and while there, replaces all three files' hand-copied magic radius (9) with the named constant it was always supposed to equal, so the indicator can't silently drift from the dot's own ring again if that radius is ever retuned.

3 · Pixel-perfect, by construction — not by screenshot diff

The oracle is the app's own layoutBlock / branchLayout — dynamically imported straight from the running Vite dev server, never reimplemented — mapped through the shape's real getShapePageTransform and editor.pageToScreen. Two independent claims per port:

  • position — the computed indicator centre lands within 1px of the live .Port dot's own getBoundingClientRect centre (steady-state noise measured under 0.6px everywhere, so 1px never flakes).
  • existence — the live overlay canvas actually has ink at a point sitting exactly on the socket's own outer edge, on the port's outward side: the one place a straight body edge never reaches, and the one place a skipped port (this bug) paints nothing at all.

Covers every primitive that carries a port: Block's port / simple / expanded / value views, ports on the left, right, top and bottom edges (a mut effect port; Loop's item outlet), a dense six-a-side stress case across every port-colour family, a connected many-to-one port with its producer-count badge, a Branch region's control ports, a Loop region's iterable/item header ports, several zoom levels, and a resize matrix for all three shapes including one real mouse-drag on the actual resize handle — the full breakdown, with screenshots, is the port outline gallery. npm run test:port-alignment (tests/port_outline_alignment_smoke.mjs) — reverting the fix turns exactly the two Simple-view "socket painted" checks red and leaves the other 172 green, which is the journey doing its one job: point at the actual regression, not just "something changed."

4 · Decision surface

Done and proved

  • Root-caused to the actual defect (a skipped case, not a coordinate bug) by measuring the real page transform against the real DOM, not by guessing from the screenshot alone.
  • Fixed in all three shape utils that own port sockets (Block, Branch, Loop); Branch and Loop had the same magic-number smell without the same live bug, hardened while there.
  • Regression-proofed twice: stashed the fix back out on the original two shapes, then again after rebuilding against a much newer main — both times the journey failed on exactly the two Simple-view checks and nothing else, restored it, watched it go green — before calling it done.
  • Rebuilt fresh against main after it gained a real Loop region mid-review — the Loop shape shipped with the identical magic-radius pattern, caught and fixed here rather than merged as a fourth copy of the same bug waiting to happen.
