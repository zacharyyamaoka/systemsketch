Why a review URL disappears after a chat ends

The observed review endpoints are healthy. The common disappearance is an ownership boundary: a track server is intentionally a child of the agent’s shell, while a published review needs a detached runtime. The detached runtime exists and works—but its implementation has not reached main.

Evidence snapshot: 20:11 PDT · localhost only · no processes stopped
Verdict: this is principally lifecycle cleanup, not an application crash. serve.sh runs Vite in the foreground and has an EXIT trap that kills its API child. When the task executor closes its shell, both endpoints correctly vanish. A retained review at :4600 has been alive after its originating task exited, showing the required detached model is sound.

Ephemeral track server

Agent working session

Generated serve.sh creates a track API in the background, starts Vite in the foreground, and traps shell exit to kill the API. It is isolated on purpose, but it is not published.

Retained review

Human-review artifact

review_runtime.py up creates an immutable detached worktree, records its URL and PID in shared Git metadata, and starts a separate session. Its worktree and board survive the agent’s terminal.

pill-autofill at :4600/:4601 is the live proof.

The exact cleanup path

1 · Task starts ./serve.sh

It selects an isolated pair of ports and starts scripts/server.py … &. The API PID is saved only in that shell variable.

→
2 · Vite is the foreground process

npx vite … --strictPort owns the shell’s lifetime. This is useful while an agent is developing: it avoids leaving uncontrolled servers and prevents port collisions.

→
3 · The agent shell ends

Bash runs trap 'kill $API_PID …' EXIT. Vite is terminated with its process group; the trap stops the API. The browser URL now fails even though the board and report files may still exist.

Deployment gap

The fix was written, then left off main

The retained-review implementation is commit 2739ea8 (track/review-runtime-lifecycle-integration). Its scripts/review_runtime.py, tests, and the track-template publishing instruction are not ancestors of current main (b4122eb).

That explains the inconsistency: one manually published review can stay up, but a new ordinary track is still instructed to use only the ephemeral serve.sh.

Important distinction

Detached is not reboot-resilient

The retained controller uses start_new_session=True; it is detached from an agent shell, but it does not install a system service or a restart policy. A machine reboot or user-session shutdown still leaves the review down until review_runtime.py up NAME runs again.

That is a separate durability tier from “does not die when the chat finishes.”

What to change when this is taken up

  1. Reconcile and merge the retained-review controller onto current main; do not merely copy its command into a task prompt.
  2. Make final handoffs label serve.sh URLs as session-only; any URL intended for later human review must be created with review_runtime.py up.
  3. Add a readiness probe to retained reviews: the current registry checks its runner PID, not both Vite and API health, and it has no automatic restart after a component failure.
  4. If reviews must survive reboot, make the retained runner a managed user service; otherwise document up as the deliberate restart command.
