The finding: green is not ready

The session began with a git heuristic — ahead of main, clean tree, no live session — which produced twelve candidates. Nine of them merged cleanly and passed npm run check. That looked like success and was not.

The authoritative signal is the shared merge-ready queue, where an author explicitly presses ready. Checked against it, seven of the nine had never been submitted by anyone. They passed a technical gate, never an authorial one.

A branch being mergeable says nothing about whether its author considers it finished. Only two of the original twelve were ever marked ready; a third author pressed ready mid-session, and that one landed too.

Taking a checkout back without destroying work

Every candidate modified README.md, which sat uncommitted in the only checkout holding main, alongside 27 other files belonging to a peer session. Landing was mechanically impossible until that cleared.

Rather than stash or discard, the working tree was snapshotted to a rescue commit built through a separate index file, so the shared .git/index was never touched and no peer's staging was disturbed. Then only the genuinely colliding files were reverted, the fast-forward applied, and the peer's hunks 3-way merged back on top.
