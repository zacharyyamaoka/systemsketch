The short version

right  What holds up

Your step 1.2 is the whole insight: worktrees cannot fix this; the only way to move faster is independently parallel tracks. That is correct, and it is the sentence the rest of the plan then stops following. Isolation is also worth having for a reason you did not claim: it gives each agent its own git index, which is the one shared mutable thing that actually bites you in a multi-session setup.

inverted  What does not

Steps 2–6 are all git topology, and git topology is precisely the part that doesn't fix it. A worktree removes the conflicts git would have warned you about and leaves the ones that fail silently. And the plan's stated goal — shrink review time — is made worse, not better, by its own mechanism.

What this means in practice

You dispatch three agents. Each opens a worktree containing stock tldraw and the release plumbing. Each is asked to build a feature on top of the Block. None of them can see a Block. Each writes one.

Three days later you merge. Git reports no conflicts, because none of them touched the same lines as your uncommitted work — git cannot see uncommitted work at all. You now have four Block implementations and a clean history.

This is not hygiene advice. It is step 0, and it is unskippable. git status reports 180 entries (162 untracked); git diff reports 18 files changed, 1152 insertions(+), 498 deletions(-).

3 · You already built steps 4, 5 and 6

“Merge into preview” reads as a git operation, but in this repository Preview is not a branch — it is a release channel: an immutable, content-addressed build that release:candidate publishes and release:promote blesses. The button you describe in step 6 exists.

4 · The reframe — isolation is not independence

This is the load-bearing objection, and you have already written it down once.

“If the Block contract is still changing under the grid, finish Block first; otherwise this is Tempus disguised as parallelism.” — your project note, 31 August

A worktree isolates files. Parallel tracks require isolating contracts. Two agents in perfect filesystem isolation, both working against a Block contract that is still moving, will produce two clean diffs, a clean merge, and a broken product. Git detects edit collisions; it does not detect intent collisions, and the only detector for those is a test suite running against the merged state.

Conflict classDoes a worktree help?How you find out
Textual — two branches edit the same lines eliminated Git stops and asks. Visible, cheap, and the class you were already being warned about.
Semantic — different lines, incompatible intent no change Nothing stops. It compiles. Tests on both sides pass. You find it in the UI, later, as a bug with no obvious author.
Duplicate — both tracks build the same missing thing made likelier Isolation is what prevents each agent from noticing the other already did it.
The gate is a frozen contract, not a directory. Before a track forks, it must name the interface it depends on, name who owns it, and state that it is not being edited this week. If you cannot fill that in, the tracks are not independent and the right move is to sequence them — no amount of isolation converts sequential work into parallel work.
And SystemSketch's current lane count is 1. Every artefact in docs/ dated today — batch editing, click-to-edit, edge rebuild, port-in-window — is one feature being iterated by taste. Adopting worktrees here optimises a resource you are not short of. The repositories with genuinely separable lanes are the ones where an interface already exists between them.

5 · The trap: this plan makes its own stated bottleneck worse

You wrote “a bottleneck is basically the review time and the goal is to shrink that”, and then designed a system that multiplies producers against a single consumer. Those are the same variable pulled in opposite directions.

Why “very rich content” alone will not do it

Richness is not free — it is more for you to read. It only shrinks review when it replaces work you would otherwise have done yourself: reproducing the bug, finding the file, checking the test actually ran. A gallery that makes you admire the work is review load. Evidence that lets you skip verifying is review relief. Same page count, opposite sign.

What actually raises your service rate

  1. A machine gate before the human gatenpm run check plus the feature's own smoke test plus screenshots must pass before anything reaches you. You review taste. You never review correctness.
  2. Every ask carries its reversible default“If you say nothing I will do X, and undoing it costs one commit.” Silence becomes progress instead of a stall. This is the only move that decouples agent throughput from your attention — and vibetracks already implements it.
  3. Batch per track, not per jobOne packet with every open question, at a cadence you choose, rather than a trickle that fragments your day.
One more serialisation point. Steps 4→5→6 funnel every track through a single Preview channel you inspect one at a time. Four tracks finishing on the same afternoon means four sequential promotions. Your own pruned design from yesterday — V1 Preset Shelf, 95.6/100 — is exactly the fix: several compositions live in one Preview runtime. A track's review surface should be ?preset=block-dev on the running Preview, not its own promotion. The two designs are the same problem solved twice; connect them.

6 · The corrected pipeline

Same intent, ordered so that each step is possible when you reach it.

  1. Step 0 — commit the baselineNothing below is possible until git status is empty. Today this is the single highest-leverage command in the repository.
  2. Freeze the contract, then forkName the interface, name its owner, state the freeze window. A track that cannot name its contract is sequenced, not parallelised.
  3. One worktree per track, on track/<name>The real win is a private git index and HEAD — no more shared staging area between concurrent sessions. Merge daily; branch age is what turns isolation into semantic drift.
  4. Each track serves itself on its own port tripleDerived from the track index, written into the dispatch prompt, never rediscovered by the agent.
  5. Machine gate, then a packet with defaultsGreen check + smoke + screenshots before you are involved at all; then one batched, answerable packet where silence still moves the work forward.
  6. Merge to main, cut a candidateAlready built: release:candidate.
  7. Inspect Preview, promoteAlready built: release:promote, with release:rollback behind it.

The precondition gate, as a checklist an agent can run

Why the proof is a worktree, not a green checkout

Running npm run check in ~/systemsketch would only prove the working tree is green — which was already true before any of this, and is exactly the state that hid the problem. The claim that needed testing is that what git can hand to a new worktree is complete and green. So: fork a real detached worktree off the new HEAD, symlink node_modules, run the full suite there.
