SystemSketch · implementation report · 2026-09-01

You can change how things look now

SystemSketch ships with tldraw's style panel switched off, so until now a shape's colour, fill, stroke, size, typeface, alignment, routing and endpoints could not be changed on canvas at all. The selection pill now carries them, laid out the way FigJam lays them out, over tldraw's own styles.

12/12 browser checks 13 model unit tests 11 controls · 0 new shape props tldraw 5.3.2, unforked
The closed vocabulary is the feature. Every option is a value tldraw's style system already accepts, so the menu can only ever ask for a state a shape can actually hold — and there is no free colour picker, no stroke-width slider, no arbitrary font size. That is the same discipline you get from a formatter: fewer choices, and a board that stays coherent because of it.

3 · Copying FigJam's own values

A first pass copied FigJam's layout and drew everything else by hand. Zach looked at it and named four things that were still wrong. Each was fixed by reading the value out of FigJam rather than by judging it — and one of them was a claim of mine that turned out to be false.

The palette: I said this needed a fork. It does not.

FigJam: 21 colours in an 11×2 grid, plus a Custom picker.

I had said FigJam's palette would need a custom colour StyleProp, that a custom style prop means replacing tldraw's built-in shape utils, and that replacing shape utils is a fork — so the answer was tldraw's thirteen. That reasoning was wrong at the first step. tldraw derives the colour style from the theme: <Tldraw themes={...}> calls registerColorsFromThemes before any effect runs or any store loads, and that function calls DefaultColorStyle.addValues(...) for every colour a theme names. The palette is a documented prop on the stock component. No shape util is replaced, no schema forked.

The subtlety is in the same function's other half: it also removes any registered colour absent from every theme. A palette of only FigJam's names would unregister tldraw's grey, and a board that had ever stored a grey shape would fail validation on load. So the theme spreads DEFAULT_THEME rather than replacing it — all thirteen stay registered, and the menu simply shows FigJam's 21.

The hexes are sampled from FigJam's own popover: the centre pixel of each 24px swatch, located from the panel geometry rather than by eye.

The icons: traced, not approximated

FigJam: filled paths on a 24×24 viewBox, drawn with a CSS variable.

49 icons were captured from the running application. FigJam's option cells are unlabelled divs, so an icon's meaning only exists in its tooltip: the tracer hovers each cell, reads the tooltip, and reads the SVG under the cursor, so every path arrives already paired with FigJam's own word for it rather than by counting positions in a screenshot.

Keys are namespaced by control, and that is not tidiness. FigJam calls two different icons Triangle — a shape in the library, an outline arrowhead in the endpoint list — and a first cut keyed on the bare name, which silently drew arrowheads in the shape picker. The failure was silent because an unknown key falls back to a drawn glyph rather than throwing, so src/appearance/figjamIconMap.test.ts now fails on any name that was not traced.

Arrowheads mirror on the end control: FigJam draws one set of six and flips it for the far end, so the icon always points the way the arrow travels.

The control order follows the arrow

FigJam: Change color | Line style | Add text | Start point | Line shape | End point.

Where the arrow leaves, how it travels, where it lands. The first pass put the line shape ahead of both ends. This was already in the capture — the frames are named 04-start-point, 05-line-shape, 06-end-point — and had simply not been read.

Three line shapes, because we have three

FigJam: Elbowed · Curved · Straight.

The menu showed two. SystemSketch's own cable style has carried exactly FigJam's three all along — CONNECTION_ROUTING_KINDS is curved / straight / elbow — and the appearance menu had simply never surfaced it. It does now, so a cable reaches the full vocabulary, while a stock tldraw arrow keeps the two kinds it actually has. Offering a third to a shape that cannot hold one would be the failure mode this whole model exists to avoid.

4 · Where it deliberately differs from FigJam

6 decisions worth arguing with. Each is a consequence of building on tldraw's styles rather than a shortcut, and each is reversible.

One colour, not two

FigJam: FigJam gives a shape a separate stroke colour and fill colour, each with its own palette.

tldraw has a single color per shape that tints both. Repeating the grid under Stroke would be two controls writing one value — an alias that reads as a bug the first time you change one and the other moves. Colour lives in the colour popover only.

Every value, not FigJam's subset

FigJam: FigJam's stroke styles are Solid / Dashed / None.

A menu that cannot show a state the document can hold is broken, not tidy. tldraw's default dash is draw: hide it and a freshly drawn shape opens its own stroke popover with nothing selected. The smoke test asserts draw is present and checked for a new shape.

Size is one control, not two

FigJam: FigJam has a stroke weight (2 values, connectors only) and a font size (5 values) as separate controls.

In tldraw size drives both. Splitting them would need a custom style prop and a schema change, which is the boundary this repo deliberately keeps.

No opacity

FigJam: Neither does FigJam. Excalidraw does.

tldraw has getSharedOpacity/setOpacityForSelectedShapes ready, so this is a one-control addition whenever it is wanted — left out because the brief was FigJam first.

A Block contributes nothing, but does not block its neighbours

FigJam: n/a — FigJam has no equivalent of a Block.

A Block defines its own style props (systemsketch:blockView and friends) and none of tldraw's, so it has no appearance to edit and the Block-only pill is unchanged. The catch is that the Block branch owns the whole pill: without care, selecting a Block alongside a rectangle would put the rectangle's colour out of reach. The controls therefore ride on both branches and hide themselves when the selection has no styles.

Typography shows before there is text

FigJam: FigJam only grows the typography group once a shape actually has a label.

tldraw reports font and alignment as relevant for any geo shape, since every geo shape can carry a label. Following tldraw here means you can set the type before you type; it is a deviation, not an oversight.

5 · Live proof

npm run test:appearance drives the real product composition on an isolated board. Every change is checked against two oracles: the pill's own label, which comes from useRelevantStyles() and so round-trips through the document, and the painted stroke attribute on the canvas. A change that only moved the UI fails.

  • PASSa selected shape gets shape, paint and typography controls, in FigJam order
  • PASSthe colour popover stacks the fill row over the palette, 8px above the pill
  • PASSchoosing a colour repaints the shape and rings the chosen swatch
  • PASSthe fill row and the palette write different styles from one popover
  • PASSthe stroke popover offers every dash the document can hold, and applies one
  • PASSsize and typeface are closed named ladders, and both write through
  • PASSthe shape picker changes a rectangle into an ellipse
  • PASSeach appearance change is one history step
  • PASSa connector gets routing and endpoints, and an endpoint applies
  • PASSa selection that disagrees reports mixed instead of one shape's value
  • PASSa Block selected beside a shape keeps the shape's appearance reachable
  • PASSthe physical journey produced zero local console errors
One bug this found is worth keeping in mind. TldrawUiPopover computes its open state as open || isOpen — it ORs any open prop with its own useMenuIsOpen. A component that also tracks the state can therefore open a popover but never close it, and clicking the trigger again does nothing. The fix is to pass neither prop and style on Radix's data-state="open".
