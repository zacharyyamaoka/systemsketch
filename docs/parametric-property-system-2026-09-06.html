SystemSketch · feature report · 2026-09-06

Parametric property system

Every Block property is now honestly Python: type 0.1 and nothing changes; type chassis_width / 4 and it live-resolves against a board-wide pool of named variables, with real Python syntax highlighting the whole time — collapsed or expanded, literal or expression, there is no mode to turn it on. This is the “Expanding Cell” direction chosen from a five-way babble round.

✓ real-browser proof green

See it work

The interaction, end to end

  1. A plain literal is unchanged. 0.1 displays and behaves exactly as it does today — the BlockPort schema did not change — but now carries real syntax highlighting even collapsed and unfocused.
  2. Reference an undefined name (chassis_width / 4, nothing named chassis_width yet): a real wavy underline appears under the name, a tooltip names the exact Python error, and the reference shows up unprompted in “Variables used here.”
  3. Define it inline — type a value right into that same section — and the property resolves live, everywhere it's referenced.
  4. A board-wide Variables panel (command palette → “Show Variables”) lists every variable in one place; editing one there updates every property that references it, without touching those properties directly. Variables may reference other variables — a circular reference is a reported error, never a hang.
  5. Legacy content never breaks. A bytes-typed port whose default value is the bare word raw (today's real fixture content, no quotes) displays exactly raw, forever, with a quiet warning glyph — never rewritten, never a crash.

Review fixture

Two decisions worth knowing about

Decision 1 · data model

Evaluation is a live preview layer; nothing about storage changed

BlockPort.defaultValue stays exactly the plain string it always was — no new field, no kind: literal | expr flag. The inspector always attempts to evaluate that string as Python (satisfying “always on, no toggle”), but success or failure never changes what's stored or what codegen/export reads. This is what makes the “never break legacy content” guarantee unconditional: the real fixture corpus already contains text that isn't safe Python (raw on a bytes port, ./input on a Path port — a genuine SyntaxError) and none of it needed to change.

Alternative considered: an explicit per-port isExpression flag, opt-in only. Rejected because Zach was explicit: always on, no toggle.

Decision 2 · where globals live

The Behavior Tree Blackboard could not be reused — it's not a store

The original plan (from the babble round) was to reuse the existing Blackboard lens as the global variable pool. Research into the actual code found it isn't a data store at all: it's a derived, per-Behavior-Tree-region projection recomputed from that region's XML text on every render, with no live values (there's no BT executor) and no cross-region scope. None of that matches “one board-wide pool of named variables with real values.”

The registry is instead a new singleton utility shape (variableRegistry, src/expression/variableRegistryModel.ts) — parked off any real content, auto-created the first time anything needs it, never drawn or arranged by hand — using this repo's one proven mechanism for board-persisted custom data (shapes), the same way Behavior Tree's own XML and Code's own document already do. It's exposed as a new command-palette surface (“Show Variables”) and via the per-Block “Variables used here” section, not as something you select on canvas.

Alternative considered: promoting the existing per-Block Pill primitive (valueBlock.ts) to board scope. Pills do have real values today, unlike Blackboard, but Zach was explicit that he wanted one central registry, not a panel scoped to wherever a Pill happens to sit — the singleton shape gives that single source of truth directly.

Neither decision has landed on main yet, so no docs/peps/ entry was written per this repo's “at merge time, not before” rule — worth writing one if/when this merges.

Consistent Python highlighting, structurally

The tok-* → --ss-* color mapping that used to live only in code-block.css (private to the Code block) moved to a shared src/theme/pythonTokens.css, imported by both the Code block and the new expression field — one palette, reused, not copy-pasted — extended with a dedicated tok-variableName rule (the single most saturated color in the palette) since that's the one token this feature most needs readers to notice at a glance.

Known follow-ups (not built)

  • The Variables panel and the “Variables used here” section are functionally complete but visually plain (no drag reordering, no collections/grouping like the babble mockup's Figma-lineage variant).
  • No “click a used variable to jump into the Variables panel, focused on that row” navigation yet — wiring it would mean threading chrome state into BlockInspector.tsx, which risks a circular import between blocks/ and chrome/ and was deliberately left out rather than rushed.
  • Codegen/export still emits the raw defaultValue string verbatim (unchanged behavior) — whether a generated-Python target should instead emit the resolved value, or rely on the same names being defined in that generated scope, is a real product question for later, not decided here.
