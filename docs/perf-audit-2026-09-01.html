Why it felt slow, measured — and what is faster now

A CDP journey seeds 48 Port-view Blocks wired by 68 elbow cables, then drives eight gestures while recording frame gaps, long tasks and a sampled CPU profile. Eight per-frame wastes were found in SystemSketch's own code; all are fixed on this branch and re-measured with the same instrument.

617→33 mslongest freeze after one alt-tab
39→18 msmean frame, dragging everything
992→495 msCPU per single Block drag
895→468 msCPU per cable drag

1 · What was measured

tests/perf_probe.mjs boots the app the way every other journey does — vite, the Python host, headless Chrome — seeds the board through the development seam, and runs each gesture under three independent instruments: requestAnimationFrame timestamps for frame gaps, PerformanceObserver('longtask') for blocking, and the V8 sampling profiler at 200 µs for attribution to src/, tldraw and React. Both runs below are the same script on the same board; only the source differs.

3 · The eight findings

Ranked by what they cost per gesture. Each carries the diff the fix commit applies, read from git at build time between the two pinned commits.

1

Every window blur rebuilt the whole canvas

src/blocks/ui/stockContextMenuRoot.ts

The stock context-menu root is remounted through a React key to un-stick Radix's uncontrolled open state — and tldraw renders <Canvas /> inside that root's trigger. The remount was wired to every window blur, so each switch to a terminal and back tore down and rebuilt every shape's DOM, React tree and subscriptions. tldraw registers no blur handler of its own, so the menu registry is still exact at blur time: the remount now runs only when a menu was actually open when the window lost focus, and the existing wedge detector still catches anything that slips past on the next right-click.

617 ms longest frame and 868 ms CPU per blur before → 33 ms and 49 ms after; long tasks 2 → 0.

The document was serialised on every frame, and the workspace context re-rendered with it

The autosave listener called serializeTldrawJson on every store flush — tldraw flushes once per animation frame — and only the last copy before the 600 ms debounce was ever written. The listener now counts changes; persist serialises once, when it saves, and decides cleanliness by whether the count moved while the save was in flight. 6 · Left alone, and why

  • Stock tldraw's per-frame cost — the shapes layer re-maps every rendering shape when any shape moves. Proportional to shape count, not ours to fork.
  • backdrop-filter: blur() on the top bars, the toolbar and the full-height popout (7 declarations). Each is a compositor layer re-blurred whenever the canvas repaints. Invisible on an RTX 4080; would matter on an integrated GPU. Removing it is a taste call, so it is offered, not taken.
  • Selection menu placement reads getBoundingClientRect and queries the bottom chrome on every camera change while something is selected. Measured at ~13 ms per 1.5 s drag after the fixes — small, and unmounted during manipulation anyway.
  • The 1.5 s stat poll logs every request; the largest host logs are:
    • desktop-v2/preview/api.log — 21.8 MB
    • desktop-v2/stable/server.log — 15.2 MB
    • server.log — 13.9 MB
    • preview/server.log — 6.0 MB
    Disk, not speed. Rotating or silencing stat 200s is a one-line change in scripts/server.py if wanted.
  • Cable drags still rebind on every pointer move, which hands every reader of tldraw's bindings index a new map. That is how tldraw's own arrows work too.
