How FigJam places its contextual menu

A behaviour specification taken from the running FigJam editor, not from documentation. Every geometric claim below was measured twice — once from FigJam’s own DOM rectangles, once by finding the selection outline and the menu surface in the captured pixels — so the two numbers can disagree if either method is wrong. They did not.

18 states captured viewport 1680 × 857 · dpr 1 Chrome 149 · off-screen X display FigJam web, 2026-09-01

The whole rule in one sentence. One dark pill, 40 px tall and as wide as its controls need, is horizontally centred on the selection’s bounding box and sits 16 px clear of the selection overlay — above it by default, below it when there is no room above, clamped to a 20 px viewport margin, never scaled by zoom, and removed entirely while the pointer is dragging or resizing.

1 · What is being specified

FigJam has three separate floating surfaces. They are easy to conflate, and only the first one is the “contextual menu” that follows a selection. The other two are on-demand and anchored to the pointer or to a control.

How it is positioned in the DOM

Worth copying exactly, because it is the part that goes wrong. The menu is not a child of the canvas and is not laid out with left/top. 

// a fixed, full-viewport, pointer-events-none layer, outside the camera transform
<div class="window_positioner--positionerRoot"  position: fixed; inset: 0>
  // one positioner per floating surface; screen-space translate only
  <div position: absolute; left: 0; top: 0;
       transform: translate(469.85px, 213px)>
    <div class="whiteboard_inline_menu--toolbarPrimitive"
         role="toolbar" aria-label="Selection Properties Menu">…</div>
  </div>
</div>
Two consequences. Because the positioner sits in a viewport-fixed layer and carries a plain screen-space translate(), the menu can never inherit a camera transform, and its size can never scale with zoom. Any implementation that mounts the menu inside a camera-transformed layer, or inside a container whose origin is not the canvas viewport’s top-left, will place it correctly at one camera position and wrongly at every other.

3 · Placement

Four rules, in this order: centre, offset above, flip if it does not fit, clamp to the safe area. The offset is measured against the selection overlay, not the shape — which is why single shapes read as 40 px and text objects read as 16 px. 

// all values in screen pixels, all constants measured, not guessed
const GAP             = 16;   // clear of the selection overlay
const SCREEN_MARGIN   = 20;   // left, right and top viewport inset
const BOTTOM_OBSTACLE = toolBeltTop - 20;

function place(overlay, menu, viewport) {
  let x = overlay.midX - menu.w / 2;
  let y = overlay.top - menu.h - GAP;          // prefer above

  if (y < SCREEN_MARGIN) y = overlay.bottom + GAP;  // flip below

  x = clamp(x, SCREEN_MARGIN, viewport.w - menu.w - SCREEN_MARGIN);
  y = clamp(y, SCREEN_MARGIN, BOTTOM_OBSTACLE - menu.h);
  return { x, y };
}

4 · Lifecycle

The menu is not merely hidden during direct manipulation — it is removed from the document, and rebuilt against the new geometry when the pointer comes up. That is what makes dragging feel clean.

5 · What goes in the pill

The content model is the interesting half of the design, and it is strict: the pill shows the properties the selection actually has, and a multi-selection shows the intersection. There are no destructive or structural commands — no delete, no duplicate, no z-order. Those live in the right-click menu, where a mis-click is not fatal.

6 · The two neighbouring surfaces

Both reuse the same dark surface, the same 13 px radius and the same shadow, so they read as one family. Their anchoring rules are different, and deliberately so.

7 · Delta against what SystemSketch already has

SystemSketch renders its selection menu through tldraw’s TldrawUiContextualToolbar (src/chrome/SystemSketchChrome.tsx, SelectionMiniMenu). That primitive already implements most of this specification; the constants differ, and two behaviours are absent rather than merely different. The two that are absent, not just different. tldraw clamps the vertical position instead of flipping, so a selection near the top of the viewport gets a toolbar sitting on top of the shape rather than below it — visually the same failure as a menu appearing somewhere unexpected. And TldrawUiContextualToolbar only hides during manipulation when it is handed an isMousingDown prop, which SelectionMiniMenu does not currently pass, so the menu rides along during drags. Both are small, local changes: a flip branch in a wrapper that supplies getSelectionBounds, and one extra prop.

Method. A copy of the signed-in Chrome profile was launched on an off-screen Xvfb display with software WebGL and driven over the DevTools Protocol. Captures were taken on a scratch FigJam draft, at 100% browser zoom so that CSS pixels and screenshot pixels are the same unit. Nothing in any existing Figma or SystemSketch document was read from or written to.

Scope. One viewport size, one platform, the free plan, the FigJam build served on 2026-09-01. The constants (16, 20, 40, 13) held across every state captured, but they were not verified at other viewport sizes or device pixel ratios. The bottom-obstacle inset rests on a single observation.
