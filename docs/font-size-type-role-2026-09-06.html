Font size is a type role, not a pixel size

“I can have text with different size that has the same extra large setting?” — yes. Stock tldraw reads one rung name off three different type scales, so Extra large is 44px of Text, 32px of sticky note and 24px of code. The menu printed only the name. It now prints the number, and it refuses to check a row for a selection that does not share one.

The real app, one continuous take: the heading’s menu says Extra large 44, the sticky’s says Extra large 32, the Code block’s says Extra large 24. Selecting the heading and the sticky together drops every check mark and reads Mixed; one typed 40 in Custom lands the same rendered size on both.

What was actually wrong

Nothing in the canvas. The shapes were storing and drawing exactly what they claimed. The report was about the menu: it showed four names and no numbers, and it put a check mark beside Extra large for a pair of shapes that render 12px apart — 20px across the whole menu.

Why the ladders were not simply merged

The obvious fix has a tail. Making one name mean one pixel size everywhere is possible — applyCustomFontPx already writes any exact px as rung × scale — but scale is not a font property on two of the four shapes. Measured in the running app at scale 1.375: a geo rectangle’s label reaches 44px and its stroke goes 10px → 13.75px; a sticky note’s label reaches 44px and the note itself goes 200 → 275. Changing a font size would resize a sticky.

Anchoring the shared ladder on the label scale (18/22/26/32) dodges both — geo and note keep scale 1, and only text and code carry a residual, where scale is the font. That is a real option, costed at the bottom of this page. It was not taken unilaterally because it caps headings at 32px and needs newly drawn shapes normalised on create, which is a create-side-effect on every board load.

Review board

Decision surface

Done and proved

Every Font size row prints the pixels it will draw, on the selection pill and on the Block-title menu. A selection spanning two type scales reads Mixed with no row checked instead of a false Extra large. Nothing a shape stores or draws changed, and a detached .tldr still renders identically in stock tldraw.

Needs you — one question

Should the named sizes become absolute? Today they stay tldraw’s type roles and the menu tells you the number. The alternative is one ladder (18/22/26/32) where Extra large is 32px on every shape — FigJam’s model, and the zero-relearning law argues for it. It costs: headings top out at 32px on the named rungs (Custom still reaches 400), and a newly drawn Text shape has to be normalised on create or it lands off-ladder.

Recommendation: ship what is here and take the absolute ladder as a separate, reversible change if the numbers on the rows do not settle it. Default if you say nothing: no further change — the menu is honest and the Custom field already makes any two shapes exactly equal.

Deliberately not done

No configure() override of tldraw’s label font sizes: it would unify the ladders without touching scale, and it would also make a detached .tldr render at a different size in stock tldraw — the one property this whole mechanism exists to preserve. No change to the arrow-label scale (not in the menu by design). No PEP: this restores behaviour the menu should always have had, which docs/peps/README.md explicitly says is not a PEP.
