Enso, Neva and unit — what to take

Three visual/dataflow systems, read from their own sources and driven in a real browser, against the questions actually open on SystemSketch's bench right now: the loop grammar, many-to-one, the delayed cable, the literal chip, and how a region gets made. Answered 2026-09-03 — the verdicts are at the foot, and the reframe they turn on is one section above them.

Seven things to take

1

Make many-to-one a node, not a rendering rule

Neva — networks.md · issue #935

Rejected — and right

What they do

In Neva, [warm, cold] -> route is syntactic sugar. It desugars to a real FanIn component with numbered slots: warm -> fanIn[0], cold -> fanIn[1], fanIn -> route. The semantics come with it: messages “merged and received in the order they were sent”, randomized when simultaneous.

Neva's own visual-editor audit ranks this: fan-in and fan-out “desugared into fan_in/fan_out nodes and connections, visualizes without any problems”, while deferred connections are “generally an ambiguous feature”.

SystemSketch today

Three cables land on one dot. The port shows a sink count, and which cable is live is decided by an active-path rule plus a lint. Order is not represented at all — there is nowhere to put it.

The Sept 2 babble landed on transparency + a badge, i.e. it stayed a rendering answer to a structural question.

What I'd change

Superseded — Zach rejected this, correctly. A node here would lie about where the decision is made. In his words: the switching logic is determined upstream, so “putting a switch here makes you think it's determined at this point, which is just not the case… to read the dataflow DAG properly only one of those branches will ever be active.”

The reading error was mine: I treated one word as one operator. There are three, and only two of them are nodes.

  • merge — every sender live, order = arrival. Neva's FanIn. A real operator, so it deserves a shape.
  • gather — every sender live, wait for one fresh value from each, preserve order. Zach's own FR-LK-DETERMINISTIC-GATHER, implemented in lk_dora_rs. Also a real operator, also deserves a shape.
  • φ — senders mutually exclusive, exactly one live, and the choice was already made upstream by the branch. Nothing happens at the convergence point, which is exactly why it must not be drawn as a thing that acts.

So the fade + active-path rendering rule is not a rendering answer standing in for missing structure. For φ it is the honest structure: the convergence is a place where cables meet, not an operator. Neva's FanIn earns its node because in Neva every sender really is live; branch arms are not.

Cost & risk — none — nothing to build. The residual work is naming: SystemSketch's many-to-one port should know which of the three it is, and today it has one presentation for all of them. Only merge and gather would ever want a shape.

2

Consider not drawing the for-loop at all

Neva — qna.md, networks.md

Add it as the sixth column

What they do

Neva has no loop construct. A collection becomes a stream<T>; Range is an ordinary component with the signature pub def Range(from int, to int) (res stream<int>). You consume it with Map, Filter, Reduce and ForEach.

The reason streams exist at all is termination: they give a dataflow graph a way “to know when a collection ends, crucial for implementing patterns like map/filter/reduce”. The end of iteration is carried in the data, not in the border of a drawing.

SystemSketch today

The 10-variant region pass (Ten other ways to draw a Python for-loop, default v1) is rejected. The live pass, running in a peer session as this was written, derives 5 grammars from LabVIEW's auto-indexing tunnel and shift register — Wall Tunnels, Cardinality Cable, Binding Ports, Header Contract, Bare Cycle — each of which deliberately adds no Block, gate, pill node or state node.

So the direction of travel is already away from putting grammar in the frame. Still no src/loop module exists; nothing is sunk.

What I'd change

Neva is the limit case of the direction that pass is already walking — one step past Bare Cycle. If the goal is “add nothing”, the strongest version is add no loop: others is a cable carrying a stream<T>, and Reduce is an ordinary Block with seed and fold ports whose recurrence lives inside it, where step-in already goes.

Worth naming explicitly, because the three references converge here: LabVIEW's shift register, Neva's Lock and SystemSketch's z⁻¹ are the same object arrived at independently. That is strong evidence the one-turn delay is the real primitive — and that whatever else a loop grammar adds is decoration on top of it.

This is not a rejection of regions in general. Branch earns its region because arms are genuinely spatial — Blocks live inside an arm. A loop body's Blocks don't belong to the iteration that way; they belong to a function the iteration calls.

Cost & risk — nothing new to build to evaluate it — a sixth column on the comparison the peer session is already producing. The cost of skipping it is the one worth naming: a loop region is a second frame-like shape with its own layout, fold state, port host and migrations, i.e. the same order of work as Branch.

3

Move the delay to the receiving end of the cable

Neva — networks.md, deferred connections

Take it — as a split

What they do

Neva's deferred connection is written as a brace region on the wire: :start -> { 42 -> println -> :stop }, sugar for a Lock node. The rule it states in bold is the useful part:

Deferred connections defer receiving, not sending. In foo -> { bar -> baz }, bar sends immediately, but baz receives the message only after foo unlocks it.

The reason the mechanism exists is also instructive: constant nodes “are implemented as infinite loops that constantly send messages”, so something has to gate arrival.

SystemSketch today

The delayed cable is a first-class StyleProp ('data', 'async', 'delayed') with a z⁻¹ pill placed by arc length. The default is 0.5 — the midpoint — clamped to 0.05–0.95.

Mid-arc reads as “this cable is delayed”, which is true but weaker than what the reader needs to know: which end waits.

What I'd change

Default the pill to about 0.85 so it sits against the consumer. The clamp already permits it and the handle already lets an author drag it back.

But not by editing that constant. Reading the call sites shows PILL_POSITION_DEFAULT is doing two jobs at once — it is also the sentinel for “is the pill centred?” in 3 places, including the one behind the inspector's Centre the pill button (centreConnectionPill returns early when the position already equals it). Moving it would make a button labelled “Centre” put the pill at 85%.

So the change is a split: keep PILL_POSITION_CENTRED = 0.5 for the reset and the disabled-state check, and introduce a separate PILL_POSITION_DEFAULT = 0.85 for where a new pill is born.

Second, smaller: when a delayed cable is selected, that is the moment to name the seed. Neva's Lock has a sig and a data port; the seed is data. The pill is already the place a label can hang.

Cost & risk — low, but not the "one constant" it looks like from the model file — the split touches 3 call sites plus the inspector's disabled state, and the existing test asserts clampPillPosition(NaN) falls back to the default, which after the split should fall back to centred. The other judgement call is whether 0.85 crowds the arrowhead on short cables; worth eyeballing on the existing edge-vocabulary fixture first. I have not made this change — you asked for a report, and this one turned out to touch user-visible button semantics.

4

Make the literal chip a widget registry, not a chip decision

Enso — widgets/CLAUDE.md, WidgetNumber … WidgetTableEditor

Take the pattern

What they do

Enso has no separate literal node for an argument. A node is one line of code, and each argument renders as a widget chosen by a registry that walks the AST. A widget definition declares a matcher, a priority (“smaller wins”) and a score — Mismatch | Weak | Good | Perfect, where Perfect short-circuits the scan.

The shipped set is not decorative: number, checkbox, selection, vector, file browser, table editor, type cast, AI prompt. In the capture below, condition Equal 2026-09-03 opens a real calendar, and rules [ Group_By "Shop" , Sum "value" , Max "time" ] is a list editor — both inside the node pill.

SystemSketch today

The literal-argument question was babbled on Sept 1 as a single choice: name-is-the-semantics vs a grey row chip vs an off-row node. Value Blocks exist (valueBlock.ts, with inferLiteralType and a fold length), and the row chip is the current default. The pick is still open.

What I'd change

Reframe the pick. The question is not “which chip” but “who decides what a port's inline editor is”. Adopt Enso's shape: a small registry keyed on the port's inferred type, each entry with a matcher and a score, with the grey chip as the Weak-scoring fallback that always matches.

Then the Sept 1 babble stops being a fork and becomes the registry's first three entries. A bool gets a checkbox, an enum a dropdown, a path a file chip — and adding the fourth never reopens the decision.

Cost & risk — medium, and mostly upfront. inferLiteralType already exists, so the matcher has something to match on. The real cost is that inline editors inside a Block row must not fight tldraw for the pointer — this repo has already paid that lesson once (which layer owns the event), so each widget needs the same treatment click-to-edit got.

5

Derive the Branch's control ports from what crosses the boundary

Enso — collapsing.ts, detaching.ts

Take the error rule; pilot derivation

What they do

When Enso collapses a selection into a component, it does not ask for a signature. prepareCollapsedInfo computes it: the inputs are the identifiers the selection reads from outside, the output is the node no one inside consumes (“leaves are the nodes that have no outgoing connection”).

Its mirror is analyzeConnectAround: when a group is removed, connections leaving it are re-pointed at each node's own self-port source, and it returns Err rather than silently dropping an edge if any port would lose its source.

SystemSketch today

branchModel.ts states the current rule in the source itself: a control port is “Authored, never derived from a title”. The Sept 2 authoring babble recommends inspector lists plus derivation from arm code — so this is already half-recognised.

Separately, “remove frame, keep contents” already exists in src/frames/removeFrame.ts.

What I'd change

Two concrete moves. First, keep authoring as the override but derive the default: a Branch's control ports should be proposed from the cables that already cross its band, the way Enso proposes a collapsed signature. Authored wins where it disagrees.

Second, borrow the Err: “remove frame, keep contents” should refuse loudly when a cable would be left without a source, rather than healing to something plausible. That is a test assertion more than a feature.

Cost & risk — low for the failure mode (an error path and a journey), medium for derivation (it needs a definition of “crosses the band” that survives folds — and arm membership is already a meta stamp kept across folds, so the hard half is done).

6

Compose a region by drawing a ring around things

unit — Getting Started: Drawing, Composition

Prototype, don't commit

What they do

unit's gesture vocabulary is tiny and reused. Drawing is entered with click-and-hold (or Alt), and then the shape of the stroke is the command: a line out of the centre makes an output plug, a line inward makes an input, a circle makes a unit, a rectangle makes a component, and — the one that matters here — “drawing a contour around a group of nodes will compose those nodes”.

Composition and its inverse are the same gesture: long press on the background composes the selection; long press again explodes it.

SystemSketch today

A Branch region is created with the Branch tool and then Blocks are dropped into it. Detach and “remove frame, keep contents” exist as the inverse, but they are reached from menus, not from the gesture that made the region.

The house rule here is “don't invent new whiteboard interactions” — which is exactly the argument for this one: drawing a ring around things is the oldest whiteboard gesture there is, and tldraw already ships both halves (the draw tool and hit testing).

What I'd change

Add one composition path: a closed scribble that encloses two or more Blocks offers to wrap them in a Branch region. Not a new tool — the existing draw tool, plus a post-stroke check.

And make the inverse reachable from the same place. Today explode lives in a menu; it should also be the thing that happens when you erase a region's outline.

Cost & risk — medium. The stroke→enclosure test is straightforward, but the interaction has to lose gracefully: an open stroke, or one enclosing nothing, must stay an ordinary drawing. This is also the suggestion most likely to be wrong for Zach's taste, because it adds a mode-free meaning to a stroke that currently just draws.

7

Name three kinds of input — and let the save rule fall out

unit — Getting Started: Constant / Functional inputs

Take half

What they do

unit distinguishes three kinds of input on a graph, and each is a real behaviour, not a label:

  • constant — the value is not consumed; “when saving the current graph, only data in constant inputs will be persisted”.
  • functional — all must be activated before data can move in, all are invalidated together, all are consumed internally before externally.
  • iterative (the default) — no interlock at all.

Its guidance is one line: “use functional inputs for configuration, and iterative inputs for stream data”.

SystemSketch today

SystemSketch already splits the cable three ways ('data', 'async', 'delayed') but the port only one way. A literal on a port and a stream into a port are the same kind of thing today.

What I'd change

Adopt the distinction on ports, and take the persistence rule with it: a port holding an authored literal is a constant, and constants are what a .systemsketch file stores. That gives the literal-pill question (4) a semantics rather than a styling, and it answers “what does saving a board actually capture” without a new mechanism.

I would not take functional inputs yet — the interlock is real semantics, and SystemSketch has no runtime that could honour it.

Cost & risk — low if scoped to constant-vs-stream, because it names something the file format already does implicitly. High if taken whole — the functional-input interlock implies an execution model this repo has deliberately not built.

The reframe that outranks all seven

I don't want to do any deriving logic within the whiteboard. The whiteboard should remain like this hackable thing for drawing things — no linting by default. And then when we use it for rendering the Python code, I think it's the Python that is really driving a lot of it. We are NOT making a programming language like LabVIEW. We are trying to combine the flexibility and ease of use of the whiteboard with an existing mature programming language, Python. — Zach, 2026-09-03

This invalidates the frame the seven suggestions were written in, and it is worth being explicit about why. All three references are languages. Enso, Neva and unit each own their semantics end to end, so it is coherent for them to derive a signature, reject a malformed graph, or refuse a connection. SystemSketch does not own its semantics — Python does — and it is a whiteboard on the other side.

So the useful question is not “should SystemSketch adopt X” but which side of the seam X belongs on:

Whiteboard side — stays dumbPython side — may be rigid
Drawing, wrapping, grouping, moving, naming. Cheap, reversible, permissive. A half-finished sketch must stay legal. Types, arity, derivation, validation. Anything that can be wrong.
No lint. No inference at draw time. No refusal to connect two things. Signatures derived from code; diagnostics that come back from a real parse.

Re-sorted against that seam, the seven land differently. Suggestion 5 (derive a Branch's control ports) was the clearest violation — it puts inference in the drawing layer, and Zach rejected it outright. Suggestion 4's widget registry is only legitimate as a rendering of what Python already said, never as type inference performed by the canvas. Suggestion 1 turns out to have been wrong for an unrelated and better reason (below). Suggestion 6 survives cleanly, because wrapping a selection is a pure drawing move that derives nothing — which is presumably why it is the one that got a build order.

Enso is the interesting counter-example rather than a refutation: its own answer to “where do semantics live” is that the graph is the source text. That is the tar pit the vault already flags. SystemSketch's answer — keep them separate, let Python drive the rigid half — is the cheaper bet, and it is the reason most of what these three do well is not transferable wholesale.

What I would not copy

  • unit's five colour modes (Add/Info/Data/Remove/Change on SQADF). It is a beautiful compression — one gesture, five meanings — but it is a second modal system beside tldraw's tools, and it is precisely the “new whiteboard interaction” the house rule exists to prevent. The principle (reuse a gesture under a modifier rather than add a gesture) is worth keeping; the mode ring is not.
  • Enso's full text ⇄ graph round-trip. Enso's synchronisation is genuinely the best-engineered version of this — composed edits, an exact-equality gate, inverse-edit rollback, a persisted ID map. It is also, as the vault already records, the tar pit that consumed MPS, Enso and Intentional Software. SystemSketch is not a source editor and should not acquire one by accident.
  • Neva's array-port index discipline (“there must be no holes; always start at [0]”). Correct for a compiler, hostile on a canvas where a user deletes the middle cable of three. If merge slots arrive (1), they should compact — the way port rows already do.
  • unit's live values on the wire — the 0 drawn at the pin in the first unit capture above. It is lovely, and it depends on a running program. The flight recorder is the honest local version of this, and it already exists.

Verdicts — 2026-09-03

All seven answered. Two survive, one was rejected for a reason better than the suggestion, and the rest were already solved or against the grain.

#VerdictWhat actually happens
1 many-to-one as a node Rejected — and right A node would relocate the decision: the switch is upstream, and only one arm is ever live. Three operators wear the name — merge and gather are real and deserve shapes; φ is not an operator and must stay a fade. Nothing to build.
2 no loop, just a stream Noted, live Resonated while getting the for-loop working. Leaning read-only body, with step-in retained for loops that hold a lot of function code. Stays a column in the LabVIEW comparison rather than a build order.
3 move the z⁻¹ pill to the consumer Rejected 0.5 is fine — it is draggable, and the middle is a reasonable place to start. The PILL_POSITION_DEFAULT overloading is therefore moot; no split needed.
4 literal chip as a widget registry Half — explicitness wins “I like making data source explicit. Yes it's more verbose but that is the point.” So explicit value nodes stay; Enso's compression of an argument into an inline widget is not wanted for data sources. A registry may still decide how a value renders once it is there — but only as a rendering of what Python said.
5 derive Branch control ports Rejected — see the reframe above No deriving logic in the whiteboard. This is the boundary principle, not a one-off no.
6 turn a selection into a container Approved — prototype 5 variants Reframed from a drawn contour to a command: right-click → turn group into frame / Block / visual group, the way FigJam already does. Five variants are being babbled; the existing Wrap in new section (Ctrl+S) is the affordance to extend.
7 three kinds of input Already built Constants already show default values, and the functional/iterative split is already carried by port rows. Zach's framing: each iterative arrival is really its own function with its own callback handler.
